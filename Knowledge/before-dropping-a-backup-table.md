# バックアップ表を消す前に、何を数えるか

`DROP TABLE` は戻せない。「もう要らないはず」で消さずに、**消したときに何を失うか**を数える。
数えるのは**2つを分けて**＝⑴**行が失われるか** ⑵**値が失われるか**。
この2つは別の話で、**片方だけ見ると判断を間違える**。

## 1. ⑴行＝「主キーで元の表に無い行」を数える

これが **0 なら、「消えた人を取り戻す」用途での価値は無い**（＝当時いた人は全員いまもいる）。
**ここが 1 以上なら、そこに**しか**無いものがある**＝消す前に何なのかを見る。

★**この数は、値の違いとは無関係に効く。** 先に出す。

## 2. ⑵値＝「ある行の、共通の列の値が違うか」を**列ごとに**数える

★**全体で「N行違う」だけでは何も決められない。** 列ごとに数えて、**違いの正体**まで降りる。

★★**値が違うのは「壊れている証拠」ではなく、「直した証拠」のことがある。**
古いバックアップほどそうなる。**直したのが自分たちなら、
バックアップが持っているのは「直す前の、壊れていた値」**。

実例＝107行のうち106行が違ったが、中身は全部これだった：
- `self_character_id` 104行…**旧が全部 4大タイプの頭**（分類が実質24種に縮退していた壊れた値）
  → 新は21タイプ（**こちらが意図して直した**）
- `disc_*` 1行…合計 6 → **8.4**（配点の合計に戻った＝これも修復）
- `member_email` 1行…空 → あり（**本人が後から登録しただけ**）

→ 「106行も違う＝危ない」ではなく「**106行ぶんの、直す前の値**」。意味がまるで違う。

★**見分け方＝値の「形」を見る。** 旧と新を並べて、**旧が既知の壊れた形か**を確かめる
（`D_貢献` → `CS_貢献` のように、頭の付き方が変わっていれば一目で分かる）。

## 3. ⑶その値が、ほかに残っていないかを探す

修復をしたときに、**修復前の値を別の場所に保存していることが多い**
（修復スクリプトの `_before.json`、作業記録、git）。
**残っていれば「この表が唯一の記録ではない」**＝消す判断が軽くなる。
**残っていなければ、消すと本当に消える。**

## 4. ★一致しない行が1つでもあったら、削除 SQL を**作らない**

**デスクトップに置いた SQL は流される。** だから
**「条件を満たさないものの DROP を、とりあえず置いておく」をしない。**
止まって、**選べる形を並べて**判断を仰ぐ。

★**表が2つあって片方だけ条件を満たしたときも、まとめて止める**
（「2本入りの SQL」を1本だけにして出すと、**どちらを流したのか後から分からなくなる**）。
**「片方だけなら今すぐ出せます」と添えて、次の指示で出す。**

## 5. 「戻す」SQL を作らない／名前にも書かない

`DROP TABLE` に戻しは無い。
**戻せないものを「戻す」と呼ばない**（名前に `戻す` と書くと、あると思われる）。
**戻せないことは、当てる SQL の先頭コメントに書く。**

## 6. 消す側の SQL に、照合の件数を焼き込む

「いつ・何を数えて・いくつだったから消してよいと判断したか」を
**当てる SQL の先頭コメントに書く**。
あとから「なぜ消したのか」を追えるのは、**そこにしか残らない**。

---

★**残すリスクも、ちゃんと天秤に載せる。**
古い写しにメール・自由記述・トークンが入っていれば、**要らないものを置いておくこと自体がリスク**。
「消すのが不可逆だから残す」だけで決めない。
