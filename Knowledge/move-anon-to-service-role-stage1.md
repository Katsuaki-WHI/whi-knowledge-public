# anon を service_role に寄せる段（RLS 4段の第1段）で踏む5つの穴

RLS を掛ける前に「アプリの読み書きを anon から service_role へ移す」段は、
**見た目が何も変わらないので『通った』と言いやすい**。
実際には**気づかずに挙動が変わる場所**がいくつかある。順に書く。

## 1. 置き換える前に「その関数が触る表」を全部数える

anon → service_role は**権限が広がる向き**の変更。
中核表（いま RLS 無効・anon 全開）だけを触っている関数なら**返る行は1行も変わらない**が、
同じ関数が**別の守られた表**（RLS 有効・ポリシーは service_role だけ）も触っていると、
**いままで落ちていた問い合わせが成功するようになる**。

→ **関数ごとに「クライアントの変数名 → 触る表」の対応を機械で出してから**置き換える。
1ファイル一括の置換はしない。

★実例＝削除処理の中の `purchases` の1行が、anon のため**毎回 RLS で落ちていた**
（警告をログに出して先へ進み、最後の親レコード削除の CASCADE で結果的に消えていた）。
service_role にすると**その行が実際に効く**。
消える行は同じだったので実害はなかったが、**気づかずに出していたら「なぜ急に効き出したか」を誰も追えない**。
→ **コードにそのままコメントで残す**。

## 2. 「鍵を引数で受け取る部品」は触らない。渡す側を直す

外部サービスの取り込み口のような**壊すと怖い部品**は、たいてい
`function f(supabase, …)` の形で**鍵を外から受け取る**。
→ **部品は1バイトも触らず、呼び出し元を service_role にする**だけで一緒に寄る。

ただし**呼び出し元が1つだけであることを grep で確かめる**（複数あると片方だけ寄る）。
検査には**「鍵を引数で受け取る部品」の一覧を、渡す側の名前つきで書く**
（数で「11行ある」と書くと、次の人は中身を見ない）。

## 3. `cookies()` が消えて、ページ／ルートが静的化する

Next.js の cookie 付きクライアント（`createServerClient` + `cookies()`）は、
**DB の鍵としてだけ使っていても、副作用で「このルートは動的」と宣言している**。
service_role クライアントに替えると `cookies()` が消え、
**ビルド時に焼き付けられて値が固まる**ことがある（カウンターや一覧が更新されなくなる）。

→ **置き換えの前後でビルドのルート表（○/●/ƒ）を丸ごと diff する。**
変わるものには `export const dynamic = "force-dynamic"` を**明示**する
（★暗黙の依存を、明示の宣言に置き換えるだけ＝挙動は変えない）。

## 4. 「読むだけの検証」でも、開くと書く画面がある

本番DBに対して実ブラウザで確認するとき、**ページを開いただけで書き込みが走る**ことがある。
よくあるのは「開いたときに固める（結晶化・再計算・自動修復）」の保険コード。

→ **開く前に、そのページから届く範囲の `update` / `insert` / `upsert` をコードで洗う。**
走る条件が分かったら、**条件に当たらないデータを本番から選んでから開く**
（例＝「全員完了かつ全員が結晶化済み」のチームだけ）。
→ **開く前と後で、関係する表の行数＋「書かれる列が埋まっている行の数」を数えて一致を示す。**
★行数だけでは足りない（列を埋める更新は行数を動かさない）。

## 5. ★検査に「鍵」を書き写すと、検査が嘘をつく

この段のために「どのステップがどの鍵で走るか」を並べたテストを先に作ると、
**鍵をテストに手で書くことになる**。すると**コードを直してもテストは古い鍵のまま**で、
「通った」と出る＝**直したことを確かめられない**。

→ **鍵は実コードから読む**（ファイルを開いて、どのクライアントを作っているかを数える）。
 - **コメントを外してから数える**（説明文に出てくる名前を拾う）
 - **鍵が1つに決まらないファイルは不合格にする**（黙って既定に倒さない）
 - 合否は「12件落ちる」ではなく**「全部通る」**で書く（完了条件そのものにする）
 - **ステップに載っていない場所の取りこぼし**を拾うため、
   **ソース全体を洗う節を別に足す**（対象外にしてよいものは**理由つきの一覧**に書く）

★**わざと壊して落ちることを必ず確かめる**（直す前の状態に戻し、検査が何件をどの名前で指すかを見る）。

## この段の「終わった」の定義

**RLS を当てた世界を模した条件で、黄金ルート（商品が成り立つ最短の道）が全ステップ通ること。**
「anon が減った」ではなく「**当てても落ちない**」で測る。

出典＝なかまクエスト 別枠1 段階1（2026-10-07・`nakama-survey/docs/claude/2026-10-07-rls-stage1.md`）。
55 か所を寄せて、模した条件が **12件落ちる → 16/16 通る**になった。

## 6. ★最後は「鍵を作る場所」を消す（呼び方で数えるのをやめる）

anon を1つずつ service_role へ寄せていくと、最後に**作り手の関数だけが残る**。
そこで終わらせず、**作り手ごと消す**と、**その種類の間違いが構造的に起きなくなる**。

実例＝最後に残った anon クライアントは**動いていないコード**が抱えていた
（呼び出し元0件・触る表が本番に存在しない）。
消したら、**作り手の関数（`createSupabaseServer`）を import する場所が0になり、
その関数自体も消せた**。

★**消す前に2つ確かめる**＝⑴**その関数を import しているのが本当にその1ファイルだけか**
（grep すると**コメントに名前が出ているだけ**の行が混ざる＝それは import ではない）
⑵**消すファイルの呼び出し元が0件か**。

## 7. ★見張りは「呼び方」でなく「鍵の名前」で数える

`createSupabaseServer()` を消しても、
`createBrowserClient(URL, ANON_KEY)` を新しく書けば**同じ穴があく**。
だから検査は**呼び方の名前**ではなく、**anon の鍵そのもの
（`NEXT_PUBLIC_SUPABASE_ANON_KEY`）が渡されている箇所**を数える。

- **一覧（allow-list）に無い作り手が1件でもあれば落とす**（理由つきで書く）
- **わざと1ファイル足して、名前つきで落ちることを確かめる**

★**同じ形のものが1つ残ることがある**＝今回はブラウザ側の anon クライアントが
まったく同じ形（呼び出し元0件）で残っていた。
**指示に無いものを勝手に消さず、一覧に理由つきで載せて見える状態にして、判断に出す。**

## 8. ★「戻したら元に戻る」の期待を、仕組みから書く

GRANT を戻す rollback を試すとき、「**戻したら読めるようになる**」と書きたくなるが、
**RLS が有効なら、GRANT を戻しても 0 行のまま**（表に届くだけ）。

→ 期待は**2段に分けて書く**＝⑴`permission denied` ではなくなる
⑵**ただし RLS が止めるので 0 行**。
★これは副産物として**「止めていたのは RLS で、GRANT は1枚うすい上着だった」ことの裏取り**になる。
（最初「読めるようになる」と書いて落ちた＝**期待のほうが間違っていた**。）
