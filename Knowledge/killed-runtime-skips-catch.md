# 打ち切られた実行では catch が走らない＝ジョブは「作っている最中」のまま残る

サーバーレス（Edge Function・Lambda 等）は、実行時間の上限を超えると**プロセスごと止められる**。
そのとき `try / catch / finally` は**走らない**。だから

```ts
try { …長い処理… } catch (e) { await markJobFailed(e) }   // ← ここに来ない
```

と書いてあっても、**ジョブは `running` のまま残る**。

★**いちばん困るのは「見分けがつかない」こと。**
`running` は「いま作っている」とも「死んでいる」とも読める。
画面は待ち続け、本人も運営も作り直せない＝**袋小路**。
（同じ形＝[[non-fatal-write-failure-and-column-mismatch]]「症状が『何も無い』ときは、
壊れている状態と正常な空が見分けられない」）

## 直し方は**3つセット**。1つでは足りない

1. **1回ごとの呼び出しに時間の上限を付ける**（`AbortSignal.timeout` ／ SDK の `timeout`）。
   超えたら**失敗として記録して終わる**。★**外部の API はいつまでも待つ**ことがある。
2. **やり直しの前に「残り時間」を見る**。足りなければ**呼ばない**。
   ★打ち切られてから気づくのでは遅い。**打ち切られない範囲でしか始めない。**
3. **見張り**＝始まってから一定時間を過ぎた `running` を failed に倒す。
   ★置き場所は「**状態を見にきたついで**」がよい（待っている人がいるときに必ず通るので、
   専用の仕掛けを増やさずに済む）。理由を残し、**completed には絶対に触らない**。

そして **UI は failed のとき「もう一度作る」が押せること**を確かめる（袋小路を残さない）。

## 数字の決め方（★上限を当てにいかない）

**プラットフォームの上限は観測しづらい**（打ち切りはログに残らない）。
だから「上限はいくつか」を当てるのでなく、**こちらが先に打ち切る**。

- 1回の上限＝**実測の最長の少し上**（実例＝最長110.5秒 → 120秒）。
- 持ち時間＝**完走が確認できている最長より上**（実例＝199秒の完走あり → 240秒）。
- ★**数字は1か所**に置き、**環境変数で上書きできる**ようにする（測り直したらコードを触らず直せる）。

## 調べ方

- **費用の台帳（呼び出しの記録）は「応答が返ってから」書く**ことが多い。
  ★だから**行が無い＝返ってこなかった**が分かる。
  ただし「呼ぶ前に止まった」のか「返りを待っていた」のかは、それだけでは分からない。
- まず**疑いを潰す**＝処理そのものが重いのか、実物で測る（実例＝マージ 0.02ms・検査 13ms＝どちらも無関係）。
