# 共有の知識ベースは同時に触られている＝`git add .` は他のセッションの作業途中を巻き込む

`~/whi-knowledge` は**複数のセッションが同時に触る1つのリポジトリ**。
AI-RULES §5 の同期手順が `git add .` なので、**自分が書いていないファイルまで一緒に commit・push される。**

## 実際に起きたこと（2026-10-02）

SQW の工事計画（`Decisions/2026-10-02-sqw2-token-build-plan.md` ほか4ファイル）を**書いている途中**に、
別のセッション（なかまの検証）が `git add .` → commit → push した。
結果、**まだ書き終えていない4ファイルが「なかまの検証」という説明文の commit に入って push された**。

- **中身は失われていない**（追記していた途中の版がそのまま入った）。
- **困るのは2つ**＝⑴**説明文と中身が合わない**（あとで「いつ・なぜ入ったか」を追えない）
  ⑵★**書き終えていないものが「記録として残った」ように見える**（次に読む人が完成版だと思う）。

## やること

1. ★**`git add .` を使わない。自分が書いたファイルだけを名前で add する。**
   （複数まとめて add すると、1つでも pathspec エラーがあると**全部が落ちる**＝[[mistakes]] 2026-06-17。
   **1ファイルずつ add して `git status` で確かめる。**）
2. ★**commit する前に `git log --oneline -3` と `git status` を見る**。
   自分が触っていないファイルが staged に入っていたら、**外す**（`git restore --staged <file>`）。
3. ★**他のセッションが自分のファイルを巻き込んでいたら、消さずに「正しい説明文の commit を足す」**
   （履歴を書き換えない＝push 済みのものを force で直さない）。
4. ★**長い記録は、書き終わるまで下書きを別の場所（作業用の一時フォルダ）に置き、完成してから Decisions へ移す**
   のが確実。少なくとも**書いている途中であることを本文の冒頭に1行書く**。

## なぜ起きるか（仕組みの話）

- 知識ベースは**セッションをまたぐ外部記憶**なので、同時に複数のセッションが開いているのが普通の状態。
- `git` は「誰が書いたか」を見ない。**作業ディレクトリに在る変更は全部が add の対象**。
- ★**「自分のセッションしか動いていない」という前提を置かない。**
