# non-fatal の書き込み失敗は気づかれない／列名は実DBと機械的に突合する

## 何が起きたか（実例）

なかまサーベイの organic（なかまクエスト連携）取り込みで、`team_members` への upsert が
**毎回失敗していたのに、誰も気づいていなかった**。

- 原因は1つだけ＝`mapDwaiUserToTeamMember` が **`team_members` に存在しない `email` 列**を渡していた
  （PostgREST は `PGRST204: Could not find the 'email' column`／SQL では `42703`）。
- 呼び出し側が **non-fatal 扱い**（`console.error` だけで `return null` を意図的に省略）だったため、
  **上位処理は成功として進み、画面も正常に見えていた**。
- 結果、**organic 15チーム中 15チームすべてが `team_members` 0行**（`survey_sessions` は正常）。
  発覚したのは、別件（役割編集）の調査で `survey_sessions` と `team_members` を突合したとき。

★皮肉なことに、コードには既に
「注: … `team_members` の欠落は自動修復されない。Phase 2 フィードバックのメンバー一覧に影響する場合は
手動対応が必要。」というコメントが**書かれていた**。つまり「欠落しうる」ことは認識されていたが、
**「いま実際に全件欠落している」ことは誰も確かめていなかった。**

## 実例2件目：読み取りでも同じことが起きた（2026-09-04 同日・WHI Admin）

**同じ日に、同じ形の不具合が読み取り側でも見つかった。**

`getMemberDetailForWhiAdmin`（WHI Admin メンバー詳細）が `coaching_schedules` から
**`week, type`** を select していたが、実列は **`week_number, schedule_type`**。

- PostgREST は `42703 column coaching_schedules.week does not exist` を返す。
- 呼び出し側は `const { data: sch } = await ...` と書いており、**`error` を受け取っていない**。
  → `sch` が `null` → `schedules = []` → **「📅 メール配信スケジュール」表が一度も表示されなかった。**
- **画面にもログにも何も出ない。** 書き込み側は `console.error` があるだけまだマシで、
  こちらは**分割代入で error を捨てているため痕跡すら残らない**。

★**なぜ長く気づかれなかったか＝「空」に見えるから。**
「まだ旅を始めていないから予定が無いのだろう」と読めてしまい、**壊れている状態と正常な空が区別できない**。
書き込み側（0行）も読み取り側（表が出ない）も、**症状が「何も無い」**という点で共通している。

| | 書き込み側 | 読み取り側 |
|---|---|---|
| 症状 | データが入らない（0行） | 表・一覧が丸ごと出ない |
| 痕跡 | `console.error`（サーバーログのみ） | **何も残らない**（error を分割代入で捨てている） |
| 誤読 | 「まだ取り込まれていないのだろう」 | 「まだ予定が無いのだろう」 |

→ **握り潰した失敗は、画面にもログにも出ない。だから「出ていない＝正常」と読めてしまう。**
この2件は**同じ根**（列名の思い込み＋失敗の握り潰し）から出た、症状違いの同じ不具合。

読み取り側の突合のやり方（コードから `.from().select()` を抜いて実DBへ投げる・データ不変）と
チェックリストは [[select-column-mismatch-audit]] に分けて置いた。

## 教訓1：non-fatal にするなら「失敗していないこと」を別途どこかで確かめる

失敗を握り潰す判断そのものは正しいことがある（今回も、ここで `return null` すると
初回アクセスで結果ページが出なくなる＝実害が大きい）。問題は**握り潰したあと放置したこと**。

- non-fatal で握り潰す書き込みには、**「本当に書けているか」を確かめる手段を必ずセットにする**
  （＝定期的な件数突合・アラート・あるいは最低限「いつ確認したか」の記録）。
- `console.error` は**サーバーログにしか出ない**。ユーザーにも運営者にも見えないため、
  誰かが能動的にログを見に行かない限り、**永久に気づかれない**。
- 「失敗しても他が動く」は「失敗してよい」ではない。**握り潰す＝観測されなくなる**と理解する。
- ★**読み取りでも同じ**＝`const { data } = await ...` と書くと **error は捨てられる**。
  空配列と「失敗して空」が区別できなくなるので、**せめて `error` を受けてログに出す**
  （出していれば、上の実例2件目はもっと早く気づけた）。

## 教訓2：書き込む列名は、実DBと機械的に突合する

「型が通る」ことと「その列が実在する」ことは**まったく別**。
今回の `email` も、戻り値が `Record<string, unknown>` だったため **TypeScript は何も検知しなかった**
（`tsc` も `next build` も PASS）。

- **書き込み先の列名は、実DBの列一覧と機械的に突合する**。目視やコードレビューでは抜ける。
- 突合は簡単にできる：
  - 実列＝`select("*").limit(1)` の返り値のキー
  - 存在確認＝`select("<列名>")` を投げて `42703` が返るかどうか（**読み取りだけで確認できる**）
- 同じチェックを、その書き込み関数が出す**全キーに対して**回す。1列でも違えば行は1件も入らない
  （PostgREST は部分的に成功しない）。

★今回、同じ突合を `survey_sessions`（全23列）と `teams`（4列）にも回した結果、
**そちらは全列実在**と確認できた＝「失敗しているのはここだけ」と**範囲を確定**できた。
バグを直すときは、直す前に**同じ種類の失敗が他にないか**を同じ方法で洗うこと。

## 教訓3：同種のバグは「隣」にもある

同じ調査で `/api/ai-report/personal` が `team_members.respondent_name`（**これも存在しない列**）を
select していることも判明した（レガシー経路のため現行UIからは到達せず、今回は対象外）。
**存在しない列を参照するコードは1箇所とは限らない。**

## チェックリスト（書き込み処理をレビューするとき）

1. この書き込みが失敗したら、**誰がどうやって気づくか**？（気づけないなら non-fatal にしない or 観測手段を足す）
2. 書き込む**全キー**が実DBに存在するか、機械的に突合したか？
3. `onConflict` を使うなら、その列に **UNIQUE 制約が実在**するか確認したか？
   （今回は `team_members_member_token_key UNIQUE (member_token)` が実在し、正しかった）
4. 戻り値の型が `Record<string, unknown>` 等で**型チェックが効かない**構造になっていないか？
5. 直す前に、**同じ種類の失敗が他の書き込みにないか**洗ったか？
