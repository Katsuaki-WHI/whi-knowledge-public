# 外とつなぐ機能は「出す」と「始める」を分けられる歯止めを先に持たせる

外部サービスを呼ぶ機能は、**コードを本番に出した日と、実際に呼び始める日が違う**。
相手側のリリース待ち・鍵の発行待ち・運用の段取り待ちで、ふつうに数日から数週間空く。

歯止めが無いと、その期間を**「まだ出さない」で埋めることになる**。
すると**出すものが溜まり、一度に出す量が増える**（戻すときにどれが原因か分からなくなる）。

## やること

**設定が無ければ動かない・送らない。** 旗（環境変数）を1つ置き、
**既定（未設定）を OFF にする。**

- ★**既定を OFF にする**。「未設定なら ON」にすると、**設定を忘れた環境で勝手に始まる**。
- ★**`"true"` のときだけ ON** にする。`!== "false"` のような書き方にしない
  （打ち間違いが ON 側に倒れる）。

## 止める場所は「いちばん外の1か所」

**外へ出る扉（HTTP を投げる関数）の入口で止める。** 呼び出し側に書いて回らない。

```ts
// 外へ出る共通の関数の冒頭
if (!isFeatureEnabled()) return fail("feature_off", ...);
```

★**これで「呼び出しを1つ足したときに歯止めを書き忘れる」が構造的に起きない。**
呼び出しが4つあっても、扉は1つ。

**そのうえで、画面とサーバーの両方に足す。**

- **画面**＝OFF ならスイッチを出さない（押せないものを見せない）
- **サーバー**＝OFF なら拒む（画面だけ隠して API は通る、を作らない＝
  [[single-source-unlock-judgment-rpc]]）

## 判定は1か所。門を2つ作らない

似た門が既にあるなら（例＝「開発用の接続先か確かめる門」）、
**同じファイルに置いて同じ場所で読む**。

★**別々のファイルに置くと、片方だけ通る道ができる。**
しかも**どちらも単体では正しい**ので、読んでも気づけない。

## 戻し方が3段階になる（これが本当の利点）

| 軽い ←→ 重い | やること | 失うもの |
|---|---|---|
| 1 | **旗を消す**（連携だけ止める） | 何も失わない |
| 2 | コードを戻す | その版の直し全部 |
| 3 | 列を落とす（★不可逆） | 入っていた値 |

★**旗があると、いちばん軽い段が増える。**
無いと「コードを戻す」が最初の手になり、関係ない直しまで一緒に戻る。

## 検査に足すこと

旗は**書いた日は効いているが、半年後に誰かが条件を足して壊す**。
だから検査で固定する。

- **旗の値を全通り**（未設定・空・`"true"`・`"TRUE"`・` true `・`"false"`・`"1"`・でたらめ）
- ★**OFF のとき fetch が0回**（`globalThis.fetch` を数える関数に差し替えて数える）
  ＝「エラーを返す」ではなく「**外に出ていない**」を測る
- OFF のとき**外へ出る関数すべて**が同じ理由を返す
- サーバー側の拒否が OFF/ON で逆になる

★**「設定が無い」を試す節と「旗で止めている」を試す節は分ける。**
同じ節でどちらも未設定にすると、**先に当たった理由しか見えず、
もう片方が効いているのか分からなくなる**（実際に、設定を外す節で旗も未設定だったため
「設定が無いから止まった」の検査が「旗で止まった」になり、
**意図していた道を1回も通らなくなっていた**）。
→ **設定を試す節では旗を ON にし、旗を試す節では設定を揃える。**
　**2つの理由を混ぜない。**
