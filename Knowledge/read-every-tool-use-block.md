# `tool_use` は1つとは限らない。`find()` で最初の1つだけ読むと、欠けたものが「落ちた」に見える

**モデルは、1回の応答で `tool_use` ブロックを**複数**返すことがある**
（章ごとに分けて返す、など）。コードが

```js
const block = data.content.find((b) => b.type === "tool_use");
```

と**最初の1つだけ**拾っていると、**2つ目以降が丸ごと消える**。
症状は「**章が欠落している**」「**欄が空**」なので、
**モデルが書き落としたように見えて、実際はこちらが読んでいない**。

★**実例**＝英語のレポートで `tool_use` が **5個**返り、最初のブロックには
`chapter1` と `kingVoice` しか入っていなかった。残り4章は2〜5個目のブロックにあった。
生の応答を保存して初めて分かった（`stop_reason` は `tool_use`＝途中で切れてもいない）。

## やること

1. **全部のブロックを集めてマージする**（`find` ではなく `filter`）。
   同じ鍵が重なったときの決め方（先勝ち／深く混ぜる）を**先に決めて書く**。
2. **マージしたことをログに残す**（黙って混ぜない）。
3. ★**`tool_use` を読んでいる場所を grep で全部数えてから直す。**
   1箇所だけ直すと、**見ていない経路は壊れたまま残る**（[[one-pass-is-not-a-fix]]）。
4. **マージが「元が1ブロックのときに何も変えない」ことを、既存の成功応答で確かめる。**

## 調べ方＝**生の応答をそのまま保存する**

「章が欠落した」ときに、**パースしたあとの JSON しか残っていないと原因が分からない**。
`content` のブロック構成（`tool_use` が何個か）と `stop_reason` が分かれば、
**「切れた」「書き落とした」「分けて返した」のどれか**がその場で決まる。
★**止めた回の中身を捨てない**仕組み（ジョブ行に残す等）と合わせて持つ。

## 似ているが別のもの

- **二重エンコード**（章が JSON 文字列で返る）＝[[ai-tool-use-double-encoding-defensive-parse]]。
  **ブロックは1個**なので、ブロック数を見れば区別できる。
- **雛形どおりに書いた**（出力形式の見本が古いと、その古い形で返る）＝
  [[show-a-sample-and-it-gets-copied]]。**鍵の数が見本と一致する**のが目印。

## 直した場所と検査（2026-10-02・なかまクエスト）

**`tool_use` を読んでいた4箇所すべて**を、1つの関数（`src/lib/nakama/tool-use-merge.ts` の
`mergeToolUseBlocks`）に寄せた。**`find()` は1つも残っていない**（grep で確認）。

| 直した場所 | もとの書き方 |
|---|---|
| 同期・冒険バイブル（`api/nakama/bible/route.ts`） | `msg.content.find(b => b.type === "tool_use")` |
| 同期・GLB（`api/nakama/leader-bible/route.ts`） | 同上 |
| **本番の既定**＝Edge Function（`supabase/functions/generate-ai-report/index.ts`） | `data.content?.find(...)` |
| **コーチング**（`api/nakama/coaching/reply/route.ts`） | 同上（★レポートと同じ穴があった） |

### 決めたこと

- **同じ鍵が2つ以上のブロックに出たら、後勝ちにしない。重複として返し、呼ぶ側が作り直す。**
  理由＝どちらが本物か**こちらには決められない**。黙って片方を採ると、
  **中身が半分だけの章**が、形は正しいまま保存されうる（いちばん見つけにくい壊れ方）。
  ★コーチングは作り直しの仕組みを持たないので、**`tool_use` が無かったときと同じ扱い**に落とす
  （text ブロックから拾う＝会話は止めない）。
- **元が1ブロックのときは、何も変えない。**

### 検査（3つとも「わざと壊すと落ちる」ことまで確かめた）

1. **保存しておいた本物の応答**に掛け直す＝1ブロックの2本は**従来と1バイト同じ**、
   5ブロックの1本は**従来なら消えていた `chapter2〜5` が戻った**。
2. **固定ケース**（バンドルの突き合わせに追加）＝1個／5個／鍵の重複／0個／説明文の5通り。
   ★**バンドル経由の判定と TypeScript 直叩きの判定が1件も変わらない**ことを毎回見る。
3. ★**雛形と schema の突き合わせ**（`scripts/check-prompt-schema-template.mts`）＝
   **schema が必須にしている欄を、出力形式の雛形が全部見せているか**と
   **日英の雛形の欄名が完全一致するか**。
   これは**同じ日に見つかったもう1つの原因**（雛形が古いとモデルは雛形を写す）への見張り。

## もう1つの崩れ方＝**全章が1つの章の欄に文字列で入る**（二重エンコードの別の形）

**ブロックは1個**なのに、返ってきたのが `{"chapter1": "<1万字超の文字列>"}` **だけ**で、
chapter2 以降が無い。★これは**分けて返した**のでも**書き落とした**のでもない。

その文字列の中身は、**トップのオブジェクトの中身まるごと**だった：

```
{ "intro": …, … },      ← chapter1 の中身
"chapter2": { … },
…
"chapter7": { … }
```

★**`{"chapter1": ` で包んで `}` を足せば、そのまま全章のオブジェクトになる。**
よくある救済（「その文字列だけを JSON として読む」）は **`Extra data` で読めず**、救えない。

### やること

1. 章の欄が「**そのままでは読めない文字列**」のときだけ、**その鍵で包んで読み直す**。
2. 読めて、**中身が章の形**（章の鍵が2つ以上・どれもオブジェクト）なら**トップへ戻す**。
3. ★**根に既にある鍵は上書きしない**（どちらが本物か決められない）。
4. ★**展開したことをログに出す**。展開しても形が合わなければ、**従来どおり作り直しへ**。
5. ★**`tool_use` を読む関数の中に置く**＝「読み方の直し」が1か所にそろい、全経路が通る。

### 確かめ方

**保存済みの本物の応答に掛け直す**のがいちばん早い。見るのは2つ＝
**①崩れていた本が、作り直しなしに通るか ②崩れていなかった本の値が1バイトも変わらないか。**
（実測＝崩れた1本が7章そろい、**1ブロックの9本は全部「従来と1バイト同じ」**。
　なお「本当に chapter1 しか返ってこなかった本」は**従来どおり通らない**＝戻すものが無いので正しい。）

★**どのモデルでも起きる**（実測は 4.5 と Sonnet 5 の両方）。モデルを替えても残る。
