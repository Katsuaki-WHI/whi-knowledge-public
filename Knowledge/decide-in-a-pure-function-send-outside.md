# 定期通知は「送るかどうか」を純粋な関数に切り出す

1日1回の見回りで通知を送る仕組みは、**判定と送信を混ぜると確かめられなくなる**。
DB を読み、日数を数え、印を見て、メールを送り、印を書く——
これが1つの関数に入っていると、**試すたびにメールが飛ぶ**か、**何も試せない**かのどちらかになる。

**分け方**＝
- **決める**（純粋な関数）＝印・無効化・日数・状態を受け取り、**送るべきものの一覧**を返す。DB もメールも見ない。
- **動かす**（見回り）＝材料を集める → 判定に従う → 送る → 印を付ける。**判断をしない。**

こうすると、判定は**組み合わせの全数**で確かめられる。
★**期待値は実装の式を写さず、独立に組み立てる**（写すと、同じ間違いを2回書くだけになる）。

## 決めておくこと5つ

1. **送れたときだけ印を付ける。** 送れていないのに「送った」と残さない（[[record-only-what-you-observe]]）。
   ★**印だけ失敗したら次の回に二重送信になる**。それでよい——
   **届かないより、2回届くほうがまし**。ただし**黙らせずログに残す**。
2. **境目は「ちょうどその日なら送る」。**「超えたら」にすると、
   見回りの時刻のずれで**1日飛ぶ**ことがある。
3. **止めた相手には送らない。** 無効化・解約・終了の印があるものは、条件が揃っていても対象外。
4. **設定が無ければ動かない・送らない。**
   秘密鍵が無ければ**動かさず**（誰でも叩ける口を開けない）、宛先が無ければ**1通も送らない**。
   ★これで**本番に出しても、決めるまで何も起きない**＝影響0で段階的に入れられる。
5. **画面を開いたときの判定にしない。** 誰も開かなければ通知が飛ばない。

## 検証の順番

1. **全数**（純粋な関数・メール0通）
2. **印の往復**（検証用DBで、判定と印だけ。メールは送らない）
3. **門**（認証なし／違う鍵／正しい鍵／設定なし の4通り）
4. **実メール1通**——★ここだけは**本番の鍵がある環境でしかできない**ことが多い。
   検証環境にメールの鍵が無いなら、**そう報告して、本番で有効にするときの手順に回す**。
   「送れていない」を「送れた」と書かない。
