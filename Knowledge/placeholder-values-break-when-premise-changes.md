# 「合計が固定の配分」どうしを比べる前提を作ったら、全経路で合計が揃っているか点検する

**複数の項目に点を配り、合計が常に同じになるスコア**（配分型）は、
「同じ物差しなので引き算に意味がある」という性質が価値の源になる。

**その前提でものを比べる機能を作ったら、そのスコアが作られる経路を全部たどって、
どの経路でも合計が揃っているかを確かめる。**

## 何が起きるか

合計が揃っていない行が混ざると、**引き算が系統的に片側へ寄る**。
合計が小さい行と大きい行を引き算すると、差の合計が 0 にならず、**その差のぶんだけ常に一方へゲタが乗る**。

★**厄介なのは、見た目が壊れないこと。**
棒グラフは「合計に対する割合」に直して描くのがふつうなので、**絵は正しく見える**。
壊れるのは「どの項目について語るか」「差は大きいか小さいか」といった**判定**だけで、
例外も出ないし、エラーログにも残らない。

## なぜ起きるか＝「仮の値」は前提が変わると壊れる

合計が揃わない行は、たいてい**仮の値（プレースホルダ）**である。
置いた当時には、必ず**「ここは表示に使わないから適当でよい」という前提**があった。

```
昔：この列は補助情報。主表示は別の列だから、仮の値でよい
いま：この列どうしを引き算して意味を出す機能ができた
   → 前提が崩れているのに、仮の値はそのまま残っている
```

**前提を変える機能を作った人は、その前提に乗っていた仮の値の存在を知らない。**
仮の値を置いた人は、あとでその前提が変わることを知らない。**両方とも悪意がない。**

## 点検のしかた

1. **そのスコアを書き込んでいる経路を全部挙げる**（通常の入力・引き継ぎ・外部からの取り込み・移行スクリプト・管理画面）。
   コードを grep するだけでなく、**実データの「合計」の分布を数える**のがいちばん早い。
2. **合計がばらけていたら、値の“形”で種類を見分ける。**
   ★**合計だけで判定しない。** 古い実データがたまたま同じ合計になることがある
   （実例：仮の値の合計と、配点方式が変わる前の実データの合計が、たまたま同じ数だった。形は違う）。
3. **仮の値をやめる。** 元の値が別の場所にあるならコピーする（計算し直さない）。
   無いなら、**黙って埋めずに記録に残す**。
4. **既存データの修復は別スクリプト（既定 dry-run）にして、件数と影響を見てから判断する。**
   「表示が変わる行／変わらない行」を分けて数えると判断しやすい。

## チェックリスト

- 比べる2つの値は、**同じ経路で作られたものだけか**。別経路のものが混ざらないか。
- そのスコアの**合計の分布**を数えたか。想定外の合計が何件あるか。
- 仮の値を見分ける条件は、**合計でなく形**になっているか。
- 仮の値を埋められないとき、**黙って落とさず記録に残しているか**。
- 直したあと、**「元と完全に一致するか」を機械で確かめたか**（配分・生回答・分類結果）。
