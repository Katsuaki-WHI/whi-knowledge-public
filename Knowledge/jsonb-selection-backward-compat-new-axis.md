# jsonb の設定オブジェクトにキーを追記するだけで「軸を1つ増やす」＝DB変更・移行なしの後方互換パターン

保存済みの絞り込み条件（jsonb で持つ選択オブジェクト）に、新しい軸・条件を1つ足したいとき、**DBスキーマを変えず・既存レコードを壊さず**に実現できるパターン。

## やり方
- 選択条件を `selection jsonb = { a: [...], b: [...] }` のように**1オブジェクト**で保存しておく。
- 新しい軸が必要になったら、**キーを1つ追記**するだけ：`{ a, b, newAxis: "x" }`。
- **jsonb はスキーマレス**なので、キー追加に**マイグレーション（DDL）は不要**。列も型も変わらない。

## 後方互換の要（「欠如＝既定値」で吸収）
- 既存レコードは新キーを**持たない**（機能追加前に保存されたため）。
- **読み取り側で「新キーが無ければ既定値（＝従来の意味）とみなす」1行**を入れる：
  ```ts
  const newAxis = sel.newAxis === "x" ? "x" : "default";
  ```
- これで**既存レコードは従来と同一の解釈・同一の結果**になり、**データ移行（UPDATE で埋める等）が一切不要**。新規保存時だけ新キーを書く。
- 型・関数シグネチャも新キーを**任意（`newAxis?`）**にし、`undefined` を既定値に倒す。

## 一般化した教訓
- 「分類・絞り込みの選択」を **jsonb の1オブジェクトで保存**しておくと、後から**軸・条件を足すのが安い**（DDLなし・既存行に触らず・移行なし）。最初から `{...}` 一箱で持つ設計が拡張に効く。
- 拡張時の鉄則＝**「新キーは任意」「欠如は既定値（＝旧来の意味）に倒す」**。読み取り側の1行で吸収し、既存データは書き換えない。破壊的変更（必須化・意味変更）を避ける。
- jsonb に書くときは**オブジェクトをそのまま渡す**（`JSON.stringify` して文字列で入れない＝二重エスコード事故のもと）。
- 注意：この手軽さは「**検索・集計をアプリ側でやる（jsonbの中身を取り出してコードで絞る）**」構造だから成立する。DB側で jsonb キーを WHERE/GROUP BY する運用に寄せると、欠如キーのインデックス・NULL 扱いを別途詰める必要が出る。
