# ローカルで本番DBに繋げないとき、原因は環境ファイルの優先順位

ローカルで画面を動かして本番データで確かめたいのに、**チームが見つからない・ローディングが終わらない・404**。
コードは正しいのに動かないので、つい実装を疑ってしまう。**原因は環境ファイルの優先順位**のことがある。

## 何が起きるか
Next.js は起動モードごとに環境ファイルを読む。

- `next dev`（development）→ **`.env.development.local`** を読む
- `next start`（production）→ **`.env.production.local`** を読む
- どちらも `.env.local` / `.env` も読む

ここで **`.env.development.local` や `.env.production.local` がローカルDB（127.0.0.1）を指していると**、
本番を指す `.env.local` を用意しても**そちらが勝つ**。
シェルで `export` しても、`node --env-file=` で渡しても、**効かないことがある**。

★症状は「壊れている」ように見えない：
- 一覧が空 → **「まだデータが無い」ように見える**
- 結果ページが「読み込み中」のまま → **重いだけに見える**
- 招待URLが 404 → **URLを間違えたように見える**

★**HTTP 200 なのに中身が「見つからない」** のが特徴。ページ自体は正常に動いているので、
エラーログにも何も出ない（[[build-pass-not-runtime-ok]] と同じ型）。

## 見分け方
1. **起動ログを読む**（まずこれ。ポートが埋まっていて**別のサーバーが応答している**こともある＝`EADDRINUSE`）
2. 画面に出ている文字を見る（「Team not found」「0件」なら**接続先が違う**可能性が高い）
3. **環境ファイルの接続先をホスト名だけ確認する**（値そのものは出力しない。`127.0.0.1` かどうかだけ分かればよい）

## どうするか
★**他人の環境ファイルを書き換えない。** 一時的に退避して戻す運用は、戻し忘れると静かに壊れる。

代わりに、**確かめたいことを、環境に依存しない形に分解する**：

- **表示される値**が正しいか → 値を組み立てる関数を直接呼んで機械で照合する（DB不要）
- **描画のされ方**が正しいか → 本番の実ページを開き、**必要な部分だけローカルのファイルで差し替える**
  （ブラウザ自動化のリクエスト横取り。本番には何も書かない）
- **DBが絡む挙動**が正しいか → 本番反映後に本番で確かめる（できなかったことは正直に報告する）

★「ローカルで見られなかった」を**黙って飛ばさない**。何を確かめ、何を確かめられなかったかを分けて書く。

## ついでの落とし穴
- **`NEXT_PUBLIC_*` はビルド時に焼き込まれる。** 実行時に env を差し替えても、
  クライアント側の値は**ビルドしたときのまま**。
- **ポートが埋まっていると、自分が起動したつもりのサーバーではなく、古いサーバーが応答する。**
  「直したのに変わらない」ときは、まずここを疑う（数日前から動きっぱなしのことがある）。
