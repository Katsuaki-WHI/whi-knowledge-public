# 「テスト専用」のガードを機能そのものに掛けると、本番の機能が丸ごと止まる

## 何が起きたか

開発中に「時間を早送りするためのAPI」を作り、その先頭に
**`if (mode !== "test") return 403`** を1行置いた。

ところがそのAPIには、早送りだけでなく**進行そのもの**が相乗りしていった：
次の段階へ進む／その回のまとめを作る／完了する。
結果、**本番では機能が一度も動かなかった**。実データでも、最初の段階より先へ進んだものは**0件**。

## なぜ誰も気づかなかったか

1. **画面のボタンはモードで出し分けていなかった。** 押せるのにAPIだけが拒む。
2. ★**UIがAPIのエラーを表示していなかった**（`if (r.ok)` のときだけ処理し、失敗時は無言）。
   利用者から見ると「**押しても何も起きない**」としか見えない。
   これは**問い合わせが来ない**＝運営側にも届かない。
3. 開発とテストは常にテストモードで行うので、**開発者は一度も踏まない**。
4. ログにも出ない（403 は正常応答）。

## 直し方

**モードで機能を丸ごと分けない。アクション1つずつで決める。**

```
TEST_ONLY_ACTIONS = ["時間を飛ばす操作"]   // ← これだけ残す
if (TEST_ONLY_ACTIONS.includes(action) && mode !== "test") return 403
```

線引きの基準は **「時間を飛ばす操作か、本人の意思による操作か」**。

- **時間を飛ばす**（予定より早く通知を作る・待たずに次の日にする）→ テスト専用のまま
- **本人の意思**（始める・まとめる・終える）→ 本番でも動かす
- **上限の除外**（開発中に制限を無視したい）→ テスト専用のまま

## 本番で動かすときに必ずセットで入れるもの

テストでは開発者が1回ずつ丁寧に押す。**本番では利用者が二度押しする。**
通信が遅ければなおさら。だから、開放と同時に**二度押しで壊れない**ようにする。

| 種類 | ガード | 入れないと |
|---|---|---|
| 何かを作る操作 | 既にあれば作り直さず、いまの状態を返す | 押した回数だけ増える・毎回AIを呼ぶ |
| 一度きりの成果物 | 既にあれば絶対に作り直さない | **本人が受け取ったものが別物に書き換わる** |
| お金のかかる処理 | 上と同じ | 押すたびに課金される |

## 予防

- **「テスト用」と名づけたAPIに、あとから本番の機能を相乗りさせない。**
  相乗りさせるなら、その時点でガードをアクション単位に分け直す。
- **画面の表示条件とAPIの拒否条件を、同じ根拠から出す。**
  片方だけ変わると、症状は必ず「押しても何も起きない」になる。
- ★**UIはAPIの失敗を黙って捨てない。** 少なくとも「うまくいかなかった」と出す。
  黙って捨てると、**壊れていることが誰にも観測できない**。
- 本番の実データで **「その機能が実際に何回動いたか」を数える**。
  0回なら、使われていないのか、動けないのかを確かめる。

## 見分け方（既存コードを点検するとき）

```
① モードや環境で分岐している箇所を全部挙げる
② その分岐が「機能ごと」か「操作ごと」かを見る
③ 機能ごとに掛かっているものは、本番で到達しうる操作が混ざっていないか確認する
④ 画面側に、その機能へのボタンがモード無関係に出ていないか確認する
⑤ 本番データで、その機能の実行回数を数える（0なら疑う）
```
