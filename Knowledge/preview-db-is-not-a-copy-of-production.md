# 検証環境のDBは「本番の写し」とは限らない。始める前に列の差を機械で数える

**プレビュー／開発用のDBを使って検証を始める前に、本番とのスキーマの差を全列で数える。**
「同じアプリが繋いでいるのだから、だいたい同じだろう」で始めると、
検証そのものが成立しない状態のまま何時間も使う。

## なぜ気づきにくいか

★**壊れ方が「何も無い」なので、正常な空と見分けがつかない。**
列が足りないと PostgREST は `42703` を返し、**表が丸ごと出なくなる**。
画面は「まだ1件もありません」と出るだけで、エラーは出ない。
書き込み側も同じで、insert が静かに失敗して「作成に失敗しました」としか出ない。

さらに、検証用DBは**migration で作られているとは限らない**。
手で写して作られていると `supabase_migrations.schema_migrations` が**存在しない**ので、
「どこまで当たっているか」をDB自身に聞けない。

## やること（始める前に5分）

1. **本番と検証先の全列を取り出して突き合わせる**（`information_schema.columns`）。
   テーブル名だけでなく **`テーブル名.列名` の一覧**で比べる。
2. **型・NULL可否・既定値も比べる**（列名が揃っていても NOT NULL の有無で insert が落ちる）。
3. **migration の履歴テーブルがあるか**を見る。無ければ「手で作った写し」＝
   **いつの時点のものか分からない**と考える。
4. 差が大きいなら、**追いつかせてから検証する**。追いつかせ方は**追加のみ**
   （列を足す・表を作る）にし、**既存の行を1つも書き換えない**。
   **戻す SQL を同時に書いて記録に残す。**
5. 追いつかせたあと、**差が0件になったことをもう一度機械で確かめる**
   （「足したつもり」で終わらせない）。

## 実例（2026-10-02・なかまサーベイ）

Vercel Preview が繋ぐ開発用DBは、**2026-07-08 に作られたきり**で、
以降の migration が1つも当たっていなかった。しかも中身は**別プロダクト寄りの先祖**で、
本番には無い表・列（`survey_answers`・`qualitative_responses`・`team_members.email` など）を持ち、
逆に**本番にあって無い列が127件**あった。

今日の検証に効くものだけでも `teams.project_token` が無く、
**チーム作成が毎回失敗する**状態だった（画面には「作成に失敗しました」としか出ない）。
当てるはずだった migration も、`nakama_projects` テーブルが無いので
`alter table` が `42P01` で落ちた＝**本題に入る前に止まる**。

→ **追加のみで本番に追いつかせ（差0件を確認）→ 本題の migration → 確認 SELECT** の順で進めた。
既存の行（1チーム・2セッション）は1つも変わっていないことを前後の件数で示した。

## 関連して効いた判断

- **本番DBは読むだけ**（`information_schema` の SELECT のみ）。差分を取るためでも書かない。
- **接続の向き先を変えたら、作業後に必ず戻す**（戻したことを、戻した値と一緒に報告する）。
