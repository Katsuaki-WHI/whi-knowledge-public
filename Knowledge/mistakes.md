# mistakes.md - 再発防止の核

かつさんから明示的に訂正された、再発しうるパターンを記録。
新規追加は AI-RULES.md の「3. mistakes.md への追記ルール」3条件を満たすときのみ。

---

## 2026-05-19：Build PASS は本番OKを意味しない

**NG**：`npm run build` が成功したら「実装完了」と報告する
**Correct**：ビルド成功後、必ずブラウザベースの実HTTPリクエストフローで動作確認してから「実装完了」と報告する
**Trigger**：Next.js/RSC（React Server Components）を使うプロジェクトでの実装完了報告時。
RSCマーシャリング違反はビルド成功でも本番でエラーになるため、ビルド成功だけでは品質を担保できない。

## 2026-05-19：「調査済み・正常」報告を鵜呑みにしない

**NG**：Claude Codeが「動作確認しました、正常です」と報告したら、それで完了扱いにする
**Correct**：ブラウザベースの実HTTPリクエストフローで、かつさんもしくはClaude Code自身が実際に画面・APIを叩いて確認する
**Trigger**：実装完了報告・バグ修正完了報告のとき。
過去に「正常」報告のあと本番で再現した事例あり。

## 2026-05-19：APIエラー時の連打でコストが跳ねる

**NG**：APIエラー発生時、原因究明前に再実行を繰り返す
**Correct**：エラー発生時はまず原因究明。Spend Limit設定とアラート閾値を必ず設定。連打しない。
**Trigger**：Anthropic API・OpenAI APIなど従量課金APIのデバッグ時。
過去に予期せぬコスト消費が発生した。詳細は [[api-cost-management]]。

## 2026-05-20：マスター移行時は旧参照を全使用箇所grepで総点検する

**NG**：マスターデータを新旧で移行するとき、一部のセクション・コンポーネントだけ
旧マスター参照を残す
**Correct**：移行時は旧参照（旧関数名・旧配列名・.find()等）を src/ 全体で grep し、
全使用箇所を一覧化してから移行する。移行漏れがあると、旧マスターに無い値を引いた
特定ユーザーだけ表示が欠ける（他ユーザーは正常なので気づきにくい）。
**Trigger**：マスターデータの新旧移行時・getXxx系の参照関数を差し替えるとき。
**実例**：なかまクエスト「お主のキャラクター」セクションが getCharacter()（旧21件マスター）
を参照したままで、C_貢献（新126件マスターのみの値）を持つメンバーだけカードが空白になった。
原因はデータ欠損ではなくコードの移行漏れ。getCharacterById()（126件対応）へ切替で解決。

## 2026-05-29：Supabaseには2層のタイムアウトがある（pg_cron＋timeout延長で回避）

**NG**：大規模集計を SQL Editor で実行し「upstream timeout（~60秒）」、pg_cron に逃がしても「きっかり2:00で失敗」を繰り返す
**Correct**：Supabaseのタイムアウトは**2層・別レイヤー**と認識する。①ゲートウェイ ~60秒（SQL Editorの HTTP層）→**pg_cron等**で回避。②DB statement_timeout 2分→**関数ヘッダの `SET statement_timeout TO '600s'`**（必要なら `alter role postgres set statement_timeout`）で回避。**大規模集計は最初から pg_cron＋timeout延長を前提に設計**する。SQL Editor は短いクエリ専用と割り切る
**Trigger**：Supabaseで数分かかる集計・データ移行・MV REFRESH等を実行するとき
**出典**：SQWサーベイ2 統合設計 段階D（2026/05/29）。詳細は [[supabase-statement-timeout-layers]]・[[supabase-long-running-aggregation-pattern]]

## 2026-07-03：閲覧権限は A（画面制限）と B（本人のURL直アクセス）を分ける／URL共有を一律「穴」としない

**NG**：個人結果URL（member_token付き）に本人以外がアクセスできること・本人がURLを共有して他人が見られることを、一律に「セキュリティの穴」と早合点し、塞ぐ設計にしようとする。
**Correct**：閲覧権限を2種類に**必ず分けて**考える。
- **A＝アプリ画面上の閲覧制限**（管理画面・結果画面で「誰に何を見せるか」）＝RLS/権限設計の対象。
- **B＝本人が受け取った個人結果URLへの直接アクセス・本人の意思による共有**＝**制限しない仕様**。
  「見せ合って学ぶ」ことは WHI の狙い（対話・相互学習）であり**穴ではない**。
守るべき本質は「**設定者/第三者が member_token を一覧で吸い出せないこと**」（＝A ＋ DBのanon露出遮断）であって、本人が受け取ったURLの閲覧・共有そのものは許容する。
**Trigger**：SQW/なかまの閲覧権限・RLS・匿名性を設計/調査するとき。「URLで見られる＝穴」と判断しそうになったら、それが A の話か B の話かを先に切り分ける。
**出典**：じゅんじゅんさん指摘（2026-07-03）。本番anon露出調査中、URLアクセスを一律「穴」と早合点しかけ是正。関連＝[[2026-07-03-anon-exposure-and-rls-gap]]。

## 2026-07-13：分類・判定・条件分岐ロジックは全パターン総当たり検証をセットで必ず実施する（全プロダクト共通・絶対ルール）

**NG**：分類・判定・条件分岐など「複数の結果がありうる」ロジックを、ビルド成功・画面表示が正常なことをもって「動いている」と判断する。代表ケース1〜2件の目視だけで完了扱いにする。

## 2026-07-14：セッション内の重要な調査結果・設計リストは、報告と同時にファイル保存する（Write later 禁止の徹底）

## 2026-07-17：実在データでの本番E2E確認まで「完了」扱いにしない（プローブの200は実表示の証明でない）

**NG**：存在しないID/トークンでのプローブ（HTTP 200が返る）や、curlでのシェル取得（200）をもって「本番で表示できている」と判断する。クライアント描画（React）は実在データが無いと走らないため、プローブ200は「サーバーが落ちていない」以上を証明しない。
**Correct**：ユーザー向け表示は、**実在データ（本物のトークン/回答済みレコード）で実ブラウザ描画まで**確認してから完了扱いにする。プローブ（存在しないID）の200は「サーバー到達」の確認に留め、「実表示OK」と混同しない。クライアント描画のクラッシュは Vercel サーバーログにも出ない（ブラウザ側）ため、必要なら headless ブラウザで pageerror を捕捉する。
**Trigger**：個人結果ページ等、実在データで初めて描画が走る画面の「表示できている」判断。RSC/クライアントコンポーネントの完了報告時。
**出典**：SQWサーベイ2（2026-07-17）。個人結果ページが、**存在しないトークンのプローブでは200**だったが、**実在の回答済みトークンではクラッシュ**（旧形式データ×描画ガード漏れ）。前回まで「200＝OK」と誤認していた。発見の起点は**かつさんの実メール受信テスト**（実在URLを踏んで発覚）。headless実ブラウザで `undefined.toFixed` を捕捉して原因特定・解消。

## 2026-07-17：保存データの形式を変えたら、旧形式の残存データを必ず棚卸しして移行・防御する

**NG**：保存フォーマット（JSONの構造・型）を新しくしたあと、**旧フォーマットで保存済みの既存レコードを棚卸しせず放置**する。新コードは新形式を前提に読むため、旧形式レコードで想定外の型に触れてクラッシュする。
**Correct**：保存データの形式を変更したら、(1) **旧形式の残存データを棚卸し**（本番を実測して件数・形状を確認）、(2) **移行（recompute/変換）** と (3) **描画/読み取り側の防御**（想定外の型でも落ちない）を**セットで**行う。表示側は「正しい形のときだけ動く」でなく「不正な形でも落ちない」を原則にする（WagonChartの `?.avg ?? fallback` のように）。
**Trigger**：category_scores 等・DBに保存するJSONの構造/型を変えるとき。過去データを読む画面・集計の実装/変更時。
**出典**：SQWサーベイ2（2026-07-17）。`category_scores` に**旧フラット数値形式**（`{landscape:4,…}`＝カテゴリが数値）が本番2件残存し、新コードの想定（`{avg,level}` オブジェクト）とズレて `score.avg.toFixed()` でクラッシュ。ResultsView:491の描画ガード拡張（`score.avg==null || !Number.isFinite` で非表示）＋ recompute修復（survey_answersから再計算）の**両方**で解消。棚卸しで「2件」と思っていた不備が実は26件（うちクラッシュ2・テストノイズ24）と判明＝実測の棚卸しが有効だった。

## 2026-07-17：検証は「実データ・実サイズ・実画面」で行う（極小ダミーは境界バグを見逃す）

**Correct**：アップロード・保存・生成などは、**本番で扱う実サイズ・実データ・実画面**で検証する。特にサイズ境界（Next.js Server Actions の `bodySizeLimit` 既定1MB・Vercel の ~4.5MB 等）は、境界をまたぐ実サイズで必ず試す。

## 2026-07-17：デプロイ完了報告は「対象コミットが本番に載った」確認まで含める

**NG**：ローカル検証・push だけで「デプロイ完了・本番OK」と報告する。対象コミットが本当に本番（origin/main・Vercel Production）に載ったかを確認しない。マージ漏れ・ハッシュ取り違えのまま「完了」とすると、以降の不具合を別の犯人（環境変数・キャッシュ等）へ誤診断する連鎖を招く。
**Correct**：デプロイ完了報告には **(1) 対象コミットが origin/main に含まれる（`git merge-base --is-ancestor <sha> origin/main`）(2) Vercel Production が当該コミットで Ready (3) 可能なら公開URLで実挙動** の確認を含める。ユーザーが誤ったハッシュ/ブランチ名を挙げたら、実行前に `git cat-file -t <sha>` で実在確認し、食い違いを報告してから進める。
**Trigger**：本番反映・デプロイ完了報告。ユーザーがコミットハッシュ/ブランチ名を指定してきたとき。
**出典**：SQWサーベイ2 資料ライブラリ（2026-07-17）。存在しないコミットハッシュ/ブランチ名で「反映して」と繰り返し指示され、実在確認で毎回不在を検知。実際の不具合原因はDB列名不一致だったが、途中「スキーマキャッシュ」「環境変数のタイポ版優先」等の誤診断を積み重ねた（実データで切り分けるまで遠回りした）。

## 2026-07-17：本番向けSQLを提示/適用する前に、コードが参照するテーブル名・列名と突合する

**NG**：カテゴリ表・追加列などのSQLを、コードが実際に参照する**テーブル名・列名・値・行ID**と突合せずに提示/適用する。名前がズレると、テーブルは在るのに `42703 undefined_column` でアプリが失敗する（しかも「テーブルなし」等の別メッセージに化けやすい）。
**Correct**：SQLを本番へ出す前に、コード側の `from("...")`・`select("...")`・`.eq("col", ...)`・固定ID を grep して**1つずつ突合**する。テーブル名だけ合わせても列名・値・行IDが違えば動かない。適用後は**コードと同一の接続（service_role）・同一クエリを実行して**成功を確認する。
**Trigger**：新テーブル/新列のSQLを本番へ提示・適用するとき。DBスキーマとコードを別々に育てたとき。
**出典**：SQWサーベイ2 資料ライブラリ（2026-07-17）。適用SQLが `library_categories(category_id/name_ja/name_en/icon)`＋`workshop_kits.category_id`＋行 `GUIDE-1`、コードは `resource_categories(category_key/label_ja/label_en)`＋`workshop_kits.category_key`＋`GUIDE-READING` を参照。表名だけ `resource_categories` に改名しても列名が違い 42703 継続。最終的に**コードを本番実列に合わせて**解消。

## 2026-07-17：共通の接続実装があるなら流用する。自前接続やanonフォールバックを新機能で復活させない（RLS設計に従う）

## 2026-07-18：実測スナップショットは「撮影時点の真実」。RLS等の可変状態は最新クロージング記録＋ライブ実測で再確認してから報告する

**NG**：過去の実測記録（DB master 等の「◯月◯日実測」スナップショット）を根拠に、DBの現在状態（RLS/権限/anon可視性）を断定して報告する。その後に実施された変更（RLS実装・列変更・遮断）を突合しない。
**Correct**：DBの**可変状態（RLS・GRANT・anonで何が見えるか・件数・列構成）を報告に載せるときは、①最新のクロージング記録/Decisions で「その後に状態が変わっていないか」を確認し、②可能なら**ライブで実測**（read-only の anon SELECT 等）してから断定する。実測記録には必ず「いつ時点か」を付し、時間が経った可変状態は再取得する。「実測した＝以後ずっと真」ではない。
**Trigger**：RLS/匿名可視性/権限/件数/スキーマなど、時間で変わりうるDB状態を報告・比較するとき。特に別プロダクトとの比較や、過去の DB master・監査記録を引用するとき。
**出典**：なかま回答フロー調査（2026-07-18）。「実DBはSQWもallow-allでanon読取可」と報告したが、依拠した `Decisions/db-master.md` は**2026-06-25実測**で、SQWの**RLS全4段anon遮断は2026-07-14に完了**していた（[[2026-07-14-sqw-rls-design-final]]）。SQW本番へ anonキーで**ライブ実測**したところコア表は「permission denied for table」＝**遮断済み**と判明し訂正。正しくは「SQW=遮断済みの参照実装／なかま=唯一の未対応（anon全開）」。教訓＝古い実測を最新状態と混同しない・可変状態はライブ再確認。関連＝[[2026-07-18-nakama-response-flow-and-rls-audit]]。

## 2026-08-16：long-running なポーリングループには必ずタイムアウト（時間・回数の二重上限）を設ける

**NG**：デプロイ完了などの外部状態を待つポーリング処理（例：`vercel ls --prod` の出力を grep して `Ready` を待つループ）を、抜ける条件だけ書いて上限なしで仕掛ける。条件が満たされてもループから抜けない不具合があると、無限に回り続ける（実例＝デプロイ成功後も終了せず**1日半以上**バックグラウンドで回り続けた）。
**Correct**：long-running なポーリングを仕掛けるときは、必ず**タイムアウト（時間の上限・例：最大10分で打ち切る）**を設ける。加えて、条件が満たされても抜けない場合に備えて**回数上限（反復回数の上限）**も入れる＝時間と回数の二重の打ち切りを持たせる。打ち切り時は失敗として明示ログを出す（黙って回り続けさせない）。
**Trigger**：Vercel/CI のデプロイ・ビルド完了待ち、外部状態の変化待ちなど、条件成立を待つループやバックグラウンドのポーリング処理を書くとき。セッション終了時・「バックグラウンド残存なし」を報告する前。
**出典**：デプロイ完了待ちポーリング（2026-08-16）。`vercel ls --prod` を grep して `Ready` を待つループがデプロイ成功後も終了せず1日半以上バックグラウンドで稼働し続けた。
**再発（2026-08-23）**：同じパターンが再発。`until` ＋ `grep` ＋ `sleep 3` の待ちループ（バックグラウンドシェル b06rna1vk）が**3日5時間**稼働し続けた。**検知が遅れた理由**＝プロセス一覧（`ps`）には現れず、Claude Code の「shell details」画面（↓ to manage）でしか見えなかった。`ps` でのスキャンだけでは「残存なし」と**誤判定**する（実際、この日 `ps` スキャンをもって「残存なし」と報告したが誤りだった）。
**追加ルール①（無限形の禁止）**：待ちループを書くときは必ず「**回数上限つき `for` ループ＋達成できなければ失敗ログ**」の形にする。`until`／`while` の無限形は使わない。
**追加ルール②（残存確認の手段）**：セッション終了時・および「バックグラウンド残存なし」を報告する前に、必ず **Claude Code のバックグラウンドシェル一覧そのもの**を確認する。`ps` のスキャン結果をもって「残存なし」と報告しない（`ps` に出ないループがある）。

## 2026-09-04：価格・税率などの定数を画面ごとに自前で持たない（単一の参照元を使う）

**NG**：価格を「1箇所に集約した」あとで作った画面が、**自前の定数を持ってしまう**。
集約したファイル（`pricing.ts`）を直しても、その画面だけ古い値のまま取り残される。
**Correct**：価格・税率・しきい値など**「正が1つしかない値」は、必ず単一の参照元から読む**。
画面側で `const UNIT = 500` のように**書き写さない**。掛け算（合計）が要るなら、
参照元に**数値と整形関数の両方**を置いて画面はそれを呼ぶだけにする。
そして**集約したときは、その値を使っている画面を全部 grep して、参照に置き換わったか確認する**
（正典を作っただけでは、後から増えた画面が自前の値を持つ）。
**Trigger**：価格・税率・しきい値・段階の境界など、複数画面に出る数値を変更・集約するとき。
新しく「合計」「N人分」を表示する画面を作るとき。
**出典**：なかまサーベイ 一括購入モーダル（2026-09-04）。モーダルが
`UNIT_AMOUNTS = { jpy: 500, usd: 5, eur: 5 }` を**自前で持ち** `pricing.ts` を参照していなかったため、
2026/06/11 の税込化（¥500→¥550）から**このモーダルだけ取り残されていた**。
**3人なら表示¥1,500・請求¥1,650**＝表示が実際の請求より安く、**不当表示になりうる**状態が約3ヶ月続いた
（Stripe 側は price_id 基準で正しく¥550を請求していた）。
→ `pricing.ts` に `PRICE_UNIT_AMOUNT` / `formatTotalPriceLabel` を足して一本化し、
本番の Stripe セッションを作って `amount_total 1100` と表示 `¥1,100（税込）` の一致を照合（決済はせず）。
★関連＝[[stripe-price-change-procedure]]（表示と price_id を必ず両方揃える）・
[[mistakes]] 2026-06-10（基準値は1箇所に集約し、変更時は依存ロジックと文書を連鎖再算出する）。
**2026-06-10 は「集約する」話、本項は「集約したあと、参照していない画面が残る」話**で、対になっている。
