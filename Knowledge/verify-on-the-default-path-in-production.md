# 生成経路が2つあるとき、検証は「本番の既定経路」で通す

## 何が起きたか

AI生成に **同期（サーバーがその場で呼ぶ）** と **非同期（ジョブを積んで別プロセスが呼ぶ）** の
2つの経路があった。ローカルの既定は同期、**本番の既定は非同期**。

出力の項目（フィールド）を1つ増やしたとき、**その項目を宣言しているスキーマが2箇所にあった**のに、
**同期側にだけ**足した。ローカルでは何度やっても正しく出たので通したが、
**本番で作ったものからはその項目が丸ごと落ちていた。**

型チェックもビルドも通る。ローカルの検証も全部通る。**本番で作って中身を見るまで分からない。**

## やること

1. **経路が2つあるかを先に調べる。**
   環境変数で同期/非同期を切り替えている、ジョブテーブルに積む、別サービス（Edge Function 等）が
   実行する——どれも「2つ目の経路」である。**既定がローカルと本番で違うことを前提にする。**
2. **項目を足すときは「その項目を宣言している場所が他に無いか」を先に探す。**
   スキーマ・型・プロンプト・検証・表示。**1つ直したら grep で残りを探す。**
3. ★**本当の直し方は「足して回る」ではなく「1つにする」。**
   同期経路が組み立てたものを非同期にもそのまま渡す形にすれば、足す場所は1つしかなくなる。
   2箇所に置いたままでは、次に項目を足す人が同じ失敗をする。
4. **本番で1回作って、中身を見る。** 「ローカルで通った」を本番の証明にしない。
   ジョブ方式なら、**ジョブに保存された設定（スキーマ等）そのもの**を読んで確かめられる。
5. 検証スクリプトにも**その項目があるか**の検査を足す。無いと次も同じ落ち方をする。

## 見分け方のヒント

- **症状が「何も無い」**（項目が丸ごと落ちる／表が出ない／0件）のときは、
  例外が出ないので気づきにくい。**壊れている状態と、正常な空が見分けられない。**
- ローカルと本番で**同じ入力なのに出力が違う**なら、まず「どちらの経路を通ったか」を疑う。
  コードの差ではなく**経路の差**であることがある。

## 併せて

- 本番の既定が非同期だと、**同期経路に置いた保存前の検査（ゲート）も本番では通らない。**
  検査を足したなら、それも本番の既定経路に置かないと効かない。**穴として記録して運用で補う。**
- 非同期側が値を決め打ちで保存していることがある（版番号など）。
  **「どの設定で作ったか」を後から辿れなくなる**ので、経路を触るときにまとめて直す。

## ★保存前の検査（ゲート）は、本番の既定経路に入って初めて意味を持つ

「壊れたものを保存しない」「材料と食い違ったら作り直す」という検査を書いても、
**それが本番の通らない経路にあれば、本番では一度も動いていない。**
実例＝検査を同期経路にだけ置き、本番の既定は非同期だったので、**本番では一度も通っていなかった**。
しかも検査は「あるつもり」で運用ルールに書かれていたので、**あると思って読まれていた。**

- 検査を足したら、**本番が通る経路に入っているかを、実際に本番で1回動かして確かめる。**
  ジョブ方式なら**わざと食い違う入力を作って、失敗になる（保存されない）ことまで見る。**
  通ることの確認だけでは「検査が効いている」証明にならない（検査が無くても通る）。
- **検査のロジックは1本にする。** 経路ごとに写しを作ると、片方だけ古くなる。
  共有できない言語・ランタイムなら、**共有できる形（依存ゼロの純関数）に作り替えてから共有する。**
- ★**作り直しの記録は、保存を止める前に書く。** 止めてから書こうとすると例外が先に出て、
  **いちばん知りたい「作り直しても駄目だった回」の記録が残らない。**
- 検査を入れても**人が読む運用はやめない。** 機械が見られるのは「事実が食い違っていないか」までで、
  **読んで良いものになっているかは人にしか分からない。**

## デプロイ経路が別なら、コードを入れただけでは本番は変わらない

別ランタイムの関数（Edge Function 等）は、アプリ本体とは**別のコマンドでデプロイ**される。
実例＝3ヶ月前に直してコードに入れた修正が、**デプロイされておらず本番では動いていなかった。**
- **本番に上がっている版を取得して、手元のコードと差分を見てから作業する。**
- デプロイ前に**現在の本番の版を控え、戻せる状態**にしてから上げる。
