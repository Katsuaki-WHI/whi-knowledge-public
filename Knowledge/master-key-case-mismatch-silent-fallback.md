# 判定側のキーとマスターのキーで大文字小文字が違うと、エラーなしで別のデータが出る

## 何が起きたか

分類を返す関数が **小文字のキー**（`i`）を返すのに、**参照先のマスターだけ大文字**（`I`）で定義されていた。
参照は `MASTER[key] ?? MASTER.fallback` の形だったため、

- 例外は出ない
- **フォールバック先のデータが、それらしい顔をして出る**
- 20種類のうち**1種類だけ**が間違う

という形で、**誰にも気づかれずに本番で動き続けていた**。

## なぜ気づけないか

1. **エラーが出ない。** `??` で受けているので落ちない。
2. **出てくるものが「それらしい」。** フォールバック先も同じ種類のデータなので、
   読んだ人は「そういう結果なんだな」と受け取る。
3. **20分の1でしか起きない。** 自分のデータでも同僚のデータでも再現しないことのほうが多い。
4. **型チェックが素通りする。** `Record<string, T>` のキーは型で守られない。

## 直し方

- **キー名を1文字直すだけ**（中身は1バイトも変えない）。
- 直したあとは **入力空間の全数でキーが解決できるか**を確認する。
  分類ロジックは入力が有限なことが多いので、**全パターンを回して
  「出現するキー」と「マスターのキー」の集合を突き合わせる**のが確実。
- **修正前後で、他のキーの中身が1バイトも変わっていないこと**も機械で比べる。

```
① 全入力パターン → 出現するキーの集合
② マスターのキーの集合
③ ①⊆② か（欠落0件か）／②にしか無いキーは何か
④ 修正前後で、直したキー以外の中身が変わっていないか
```

## 予防

- **キー命名の規則を1つに決め、参照側で正規化しない。**
  「呼び出し側で `.toUpperCase()` を忘れないこと」を前提にした設計は、忘れた場所で静かに壊れる。
- **フォールバックを書くときは「フォールバックが採用されたこと」を検知できるようにする。**
  黙って既定値に落ちる実装は、設定ミスを永久に隠す。
- **マスターを新しく足したら、その場で全数の突き合わせを1回走らせる。**

## 同じ形の失敗

「**症状が『何も無い』／『それらしい別のもの』だと、壊れている状態と正常な状態が見分けられない**」
というパターンは、列名の不一致・権限で読めない表・握り潰した書き込み失敗でも同じように起きる。
