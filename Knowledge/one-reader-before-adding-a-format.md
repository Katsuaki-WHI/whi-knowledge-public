# 同じデータの読み方を2箇所に書かない。新しい形式を足すときは、窓口を1本に寄せてから

**同じデータを読むコードが複数あるところに新しい形式を足すと、寄せていない側が
新形式を旧形式として読み、静かに壊れる。** 形式を足す前に、**読む場所を1つにまとめる。**

## 何が起きるか

旧形式 `{a, b, c}` を読む関数が2つあり、そこへ新形式 `{x, y, z}` を足したとする。
片方だけ新形式に対応させると、もう片方は `obj.a`（存在しない）を読んで `undefined` になる。

- **例外は出ない。** 計算に混ざって `NaN` になるか、`?? 0` で 0 になる。
- **旧データだけのうちは正常に見える。** 壊れるのは新形式が初めて入った日。
- **その日は、たいてい足した本人がもう見ていない。**

## 手順

```
① 読む場所をすべて grep で洗い出す（「この形のデータを読む」コード全部）
② 読む・版を判別する・値を検証する・混ぜない を1つの窓口にまとめる
③ 既存の呼び出しを全部その窓口に置き換える
④ ★旧データで値が1つも変わらないことを、全数で機械確認する
⑤ そのうえで新形式を窓口に足す
```

★**④を飛ばさない。** 寄せた時点で値が変わっていたら、それはリファクタではなく仕様変更。

## ★寄せるときの落とし穴：窓口が必要とする入力が揃っていない

関数ごとに「取ってくるデータ」が違うことがある。片方は識別子まで取り、もう片方は値だけ取っている、など。
窓口に寄せると、**窓口が必要とする項目を取っていない呼び出し側が、黙って0件になる。**

- 寄せたあとは、**呼び出し側が窓口の要求を満たしているか**を1つずつ確かめる。
- 特に **DB から取る列を絞っている箇所**（`select` で列名を並べている等）は要注意。
- ★**「0件になった」は例外を出さない。** テストで値を見ないと気づけない。

## 版の判別は「構造」で行う。版番号に頼らない

```
新形式にしか無いキーがあるかで判別する（旧形式にそのキーは絶対に無い）
版番号のフィールドは「記録用」に持ち、判別には使わない
```

- 版番号で判別すると、**書き忘れた1件が旧形式として読まれる**。
- 構造で判別すれば、**版番号を書き忘れても壊れない。**

## 新旧を同じ集計に混ぜない

物差しが違うものを平均すると、**その形式を変えた理由そのものが再発する。**

- **新形式が1件でもあれば、新形式だけで集計する。** 旧形式は「無かった」と同じ扱いにする。
- 混ぜた結果は誰にも説明できない。

## 外から届くデータの新旧は「相手側の切り替え日」で判別する

- **こちらが受け取った日時では判別しない。** 取り込みが遅れる仕組みだと、
  **切り替え前のデータを後から取り込んだときに新形式と誤判定する。**
- 相手側の「その回が終わった日時」を保存しておき、切り替え日と比べる。
- **切り替え日が未設定なら常に旧形式／終わった日時が空でも旧形式**（どちらも安全側）。
- 相手側の日程が決まるまで、**切り替え日は本番に置かない。**

## 想定外の値は、黙って埋めない

- 読み替え表に無い値が来たら、**その1件は保存せず、必ず記録に残す。**
- 0 や既定値で埋めると、**気づけないまま別の結果が出る。**
- 全体は止めない（1件のせいで他の人の処理まで止めない）。

## 検証の型

- **旧の回帰**＝全データで、寄せる前と寄せた後の値が完全一致することを機械確認する。
- **新の単体テスト**＝読み替え表／範囲外の拒否／切り替え日の分岐（前・後・空・壊れた値・未設定）／
  集計結果が既存の計算と一致すること／新旧を混ぜないこと。
- ★**DB が返す JSON はキーの順番が変わることがある。** 文字列化して比べると
  **中身が同じでも不一致に見える**。項目ごとに比べる。
