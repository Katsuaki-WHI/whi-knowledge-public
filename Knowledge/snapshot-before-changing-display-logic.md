# 表示ロジックを変える前に、既存の結果をスナップショットで固め、バイト比較で不変を証明する

**「計算して表示していたもの」の計算を変えるとき、まず既存の結果を全部スナップショットに固める。
そのうえで、保存前と保存後のスクリーンショットをバイト比較して「1ピクセルも変わっていない」ことを証明してから、次の変更に進む。**

## なぜ

計算式を変えると、**過去に誰かが見た結果まで、黙って書き換わる**。
「前に見たときと数字が違う」と言われたとき、**何が正しかったのかを誰も再現できない**のがいちばん困る。

固めておけば：

1. **既に見た結果が、あとから変わらない。**
2. **新旧の分岐を、表示側に永久に持たなくてよくなる**（保存時点の版で固まる）。
3. **古い計算コードを最終的に削除できる**（残っていると、直した場所と効く場所がずれる）。

## 手順

```
① 保存する場所を1つ足す（列1つ・null許容・既定なし＝既存の行に影響なし）
② 「作る・読む・判定する」を1ファイルに集約する
③ ★保存するのは生の値。整形・丸め・しきい値の判定は表示のときに行う
④ 既存データを全部照合する（保存する値と、いま計算している値が一致するか）
⑤ 表示側を「保存があればそれを使い、無ければ従来どおり計算」に変える
⑥ ★バイト比較で不変を証明する
⑦ 移行スクリプトで既存分を固める（dry-run → 承認 → 適用 → 残り0を確認）
```

## ★生の値で保存する（整形後を保存しない）

- 割合・丸め・しきい値の判定は**表示のときに行う**。
- こうしておけば、**あとで境目や丸め方を変えても、保存済みを作り直さなくてよい。**
- 逆に整形後を保存すると、境目を変えた瞬間に「昔の基準で焼かれた値」と「新しい基準」が混在する。
- 判定結果（大小の区分など）を保存するなら、**元になった数値も併せて持つ**（再判定できるように）。

## ★出どころを変えない＝それは結晶化ではなく仕様変更になる

スナップショットは「**同じ値を別の場所に写す**」作業。
写すときに「こちらのほうが意味的に正しい」と出どころを変えると、**表示が変わる**。

実例：「相手からの評価が届いているか」を、意味としては「評価者が1人でもいるか」で判定したくなる。
だが現行の表示は**別の列が空かどうか**で出し分けていた。そして**評価は届いているのにその列が空の行が実在した**。
意味を優先すると、その人たちの画面が変わってしまう。
→ **現行と同じ出どころに合わせ、意味的に正しいほうは別の項目として持つ**（次の版で使う）。

## ★バイト比較のやり方

```
1. 変更前のコードに戻す（該当ファイルだけ前のコミットから取り出す）
2. 対象ページのスクリーンショットを撮る（比較したい範囲だけを要素指定で撮る）
3. 変更後のコードに戻し、スナップショットを作らせてから、もう一度撮る
4. sha256 を比べる
```

- **範囲を絞って撮る**（ページ全体だと時刻・広告・アニメーションで毎回変わる）。
- **同じ条件を2回撮って同じになるか**を先に確かめる（手法そのものが安定しているかの確認）。
- **言語 × 画面幅**の全通りで撮る。1通りだけだと、条件分岐の片側しか見ていない。

## 気をつけること

- **「開いたときに固める」保険を入れると、ページを開くだけで書き込みが起きる。**
  検証で本番ページを開くと、それだけで対象データが変わる。
  移行スクリプトの対象件数が変わったら、まずこれを疑う（**合計が変わっていなければ想定内**）。
- **移行スクリプトを、手元の一時ディレクトリのビルドに依存させない。**
  消えたら動かなくなる。実行時に自分でビルドするか、依存を持たない形にする。
- **辞書やJSONを丸ごと書き直さない。** 元から重複していたキーが**静かに1つ消える**。
  必要な1文字列だけを置き換える。
