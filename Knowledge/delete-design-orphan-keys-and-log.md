# 「消す」機能を作るときに必ず考える3つ（宛先キー・ログ・何が消えるか）

削除は取り返しがつかないのに、たいてい一番あっさり作られている。
最低限この3つを組み込む。

## 1. ★送り手側に保存されるデータは、消した人の「宛先キー」を他人の中に残す

- **形**＝`{ 相手のトークン: 値 }` のように、**キーが相手を指す**保存のしかた。
  （実例＝相互フィードバック `peer_feedback`。「自分が誰に何点を付けたか」を自分の行に持つ）
- **消すと何が起きるか**＝その人の行は消えるが、**その人「宛て」のキーは、他の人の行の中に残り続ける**。
  誰も指していないキー＝**孤児キー**。
- **見つけ方**＝「他人のデータにキーとして在るが、本体のテーブルに居ないトークン」を数える。
- **直し方**＝削除処理の中に「**同じ範囲の他メンバーから、そのキーを取り除く**」を組み込む。
  これを入れれば、新しい孤児キーはもう発生しない。過去分は一度だけ掃除する。

★**表示は変わらないことが多い**（集計が「生きている行」から数え直す作りなら、
消えた人のキーは誰の集計対象にもならない）。だから**気づかれずに溜まる**。
掃除の目的は**データの整合性**であって表示の修正ではない。
→ **掃除の前後で表示値が1件も変わらないことを実測して示す**と、安全に適用できる。

## 2. ログは「削除より前」に書く

- **後では数えられない**。その人が持っていた件数（送ったフィードバック数など）は、
  行を消した瞬間に分からなくなる。
- **記録する内容**＝日時／対象の範囲（チーム等）／対象のトークンと表示名／削除時点の状態／
  **消える副作用の件数**。
- **ログの書き込みが失敗しても削除は止めない**。ログは追跡用であって、削除の条件ではない。
- **入口ごとに別の action 名にする**（例：運営者の画面からの削除と、社内Adminからの削除）。
  同じ名前にすると「誰の操作だったか」が後から分けられない。

## 3. 確認画面に「何が消えるか」を実数で出す

- 「削除しますか？」だけでは判断材料が無い。**副作用を件数つきで**書く。
- **0件のときも書く**（「送ったフィードバックはありません」）＝副作用が小さいと分かることも情報。
- 箇条書きは**実際に消えるものだけ**にする。消えようがないものを並べると、
  読む人は全部を疑い、結局どれも読まなくなる。
- 脅さず事実を書く。**取り返しのつかなさに比例した強さ**にする。

## 4. あわせて：消せるものと消せないものを分ける

- **お金が動いたもの（購入記録・結晶化された成果物）は、運営者の操作では消せないようにする。**
  サーバー側で止める（画面の制御だけにしない）。
- **窓口を1つに決める**（削除依頼は社内Adminだけ、など）。そこでは**会計証跡を別テーブルへ
  退避してから**消す。
- ★**外部キーの `ON DELETE CASCADE` は「宙に浮く」のではなく「一緒に消える」。**
  親を消すと購入記録が**痕跡ごと消える**ので、「completed があれば削除しない」を
  サーバー側で止めることが、そのまま会計証跡の守り方になる。
