# 二重送信と重複登録の守り（旧SQWの事例・2026-10-16 共有）

★**Public へ出すときに置き換えるもの**（AI-RULES §5-1）
- 共有してくれた人の名前 → 「運用の担当者」
- 本文には**顧客名・チーム名・メールアドレス・トークンを1件も書いていない**（実測の件数だけ）。

---

## 起きたこと（旧SQW・別会社の運用）

**送信ボタンの多重押しで、回答者3名が6名で登録され、依頼メールが2通ずつ届いた。**

★**症状は2つあるが、原因は別**＝ここを分けないと直せない。

| 症状 | 原因 |
|---|---|
| **行が増える**（3名 → 6名） | 登録の口に**重複を弾くものが無い** |
| **メールが2通届く** | 送る側が**宛先を畳んでいない**（行が2つあるので2通） |

★★**行の重複を消さなくても、宛先を畳めば「2通届く」は消える。**
逆に、宛先を畳んでも**人数・回答率の分母は狂ったまま**（行が2つあるので）。
→ **2つとも別に手を打つ。**

---

## 守りの5段（★弱い順）

| 段 | 守り | 強さ | 越えられる道 |
|---|---|---|---|
| 1 | 画面のボタンを `disabled`（state のフラグ） | 弱い | ★**Server Action・API は URL を持つ**ので画面を通らずに叩ける／React の再描画が間に合わない |
| 2 | 画面で**同期的に1回に絞る**（`useRef`） | 中 | 画面側であることは変わらない |
| 3 | 確認ダイアログ（**全画面オーバーレイ**＋**一回だけ**解決する） | 中 | 同上 |
| 4 | サーバー側の**冪等**（受けた印を先に書く／**条件つき更新**で1本だけ勝たせる） | 強い | 読んで→書く形だと**同時到達で両方すり抜ける** |
| 5 | ★★**DB の（部分）ユニーク制約** | **最強** | — |

★★**5 だけが「どの経路から来ても」効く。** 1〜4 は**どこかに抜け道が残る**。
→ **お金・人数・回答が絡むものは、5 を必ず持たせる。**

### 4 の正しい形＝条件つき更新

```
update … set status = 'sending' where id = :id and status = 'pending'
→ 返った行が1行なら自分が勝った。0行なら誰かが先に取った（やめる）
```

★**読んで→書く（SELECT してから INSERT／UPDATE）は守りにならない**＝
2つ同時に来ると**両方が「まだ誰もやっていない」と見る**。

---

## ★★印（送信記録）の決まり3つ

1. **成功したときだけ印を付ける。**
   ★**届いていないのに「送った」記録が残る**のがいちばん困る（次の再送で外れる）。
2. **取りこぼしは「再送のほう」に倒す。**
   送れたのに印が付かなかった → 次に**もう一度届く**。
   ★**届かないより2回届くほうがまし。** ただし**黙らせない**（ログに残す）。
3. ★**0通で終わった理由を残す。**
   「**宛先が0人**（メール未登録）」と「**全員もう送ってある**」を区別する。
   ★区別しないと、**0通で終わった成功**が「送れた」に見える。

---

## ★落とし穴4つ（実際に見つけたもの）

### ⑴ 読んで→書く冪等は、同時到達で抜ける
受け取った印を「SELECT して、まだなら INSERT」で書くと、
**同じ通知が同時に2回届いたとき両方が処理に進む**。
→ **ユニーク制約つきの INSERT**（または条件つき UPDATE）で、**DB に勝ち負けを決めさせる**。

### ⑵ 記録に失敗したとき「進む」側に倒れていた
受付の記録を `try/catch` で囲み、**失敗したら「まだ処理していない」として先へ進む**作りだった。
→ 記録の表が落ちている間は、**何度届いても何度でも処理が走る**。
★**不可逆な処理（お金・送信）の冪等は fail-closed**（分からなければ止める）。
　ただし**その先に DB のユニーク制約がある**なら、実害は止まる＝**だから 5 が要る**。

### ⑶ 大文字小文字で「同じ人」が2人になる
件数の表示は `toLowerCase()` するのに、**実際の宛先は `trim()` だけ**だった。
→ `A@example.com` と `a@example.com` に**2通届くのに、件数は1と出る**。
★**メールは「同じものとみなす形」を1か所に決めて、数えるときも送るときも同じ関数を通す。**

### ⑷ 一回だけガードが「戻らない」
`ref` で1回に絞ったが、**例外のときに戻す処理が無かった**。
→ 通信が落ちた1回で、**「もう一度送る」を押しても何も起きない**（画面は何も言わない）。
★**一回だけガードは「どこで戻すか」を必ず決める**（成功で戻さない／失敗とエラーの両方で戻す）。
★**ガードは、黙って何もしない形になりやすい**＝**押したのに何も起きない**のがいちばん分かりにくい。

## ★検査の型（通る側だけ試さない）

| わざと起こすこと | 止まってほしいこと |
|---|---|
| 同じ通知を**2回**届ける | 2件にならない（2回目は「もう済んでいる」） |
| 同じ通知を**同時に**2回届ける | ★同じく1件（★ここが読んで→書くだと抜ける） |
| 同じ人を**2回**登録する | 行が2つにならない／なるなら**人数の分母が狂わない** |
| 送信の**途中で落とす** | 送れた人だけ印が付く・残りは次の再送で届く |
| 大文字小文字だけ違うメール | **1通**だけ届く |

★**「2回届けても1件」を見るだけでは足りない**＝**同時に**2回届けたときを見る。
★**本番の件数で確かめる**＝「重複が0件」ではなく「**重複が何組あるか**」を数える
（★**重複が1組でも実在すれば、ユニーク制約が無いことの証明になる**）。

## 実測（SQW2・2026-10-16・読み取りのみ）

| 見たこと | 数 |
|---|---|
| 名簿の行 | 335 |
| 同じチーム × 同じメールが2件以上 | **1組（2行）** |
| 同じチーム × 同じ名前が2件以上 | 6組（13行） |
| ★そのうち**回答に紐づいた行が2件以上**ある組 | ★**0組** |
| 大文字小文字だけ違う同じメールの組 | 0組 |

→ ★**回答が二重に数えられている例は無かった**（旧SQWと同じ事故は起きていない）。
→ ★**ただし重複が1組ある＝ユニーク制約は無い**（制約があれば作れない）。
　重複の2行は**6分あいて**作られていた＝**連打ではなく、手で2回登録した**形。
　★**連打の守り（画面側）があっても、「2回登録」は止まらない。**

## ★実測の結果（2026-10-16・同じ日に本番で確かめた）

### ⑴ 守りの5段のうち、何が本当に効いていたか

**本番の索引を読んで確かめた**（`pg_indexes`）。★**6つとも実在していた。**

| 索引 | 何を止めているか | 本番 |
|---|---|---|
| 決済セッションの部分ユニーク | 同じ決済を2回受けても解錠が2件にならない | ★ある |
| 支払いの部分ユニーク | 同じ支払いで解錠が2件にならない | ★ある |
| レポートの束（個人・チーム・組織の3つ） | 束が2本にならない | ★ある |
| 「いま表示する版」の部分ユニーク | 版が（束×言語）で2つにならない | ★ある |
| **名簿の（チーム×メール）** | **同じチームに同じメールが2行にならない** | ★★**無かった** |

★★**つまり「お金」と「レポート」は最強の段（DB の制約）で守られていたのに、
「名簿」だけが画面の `disabled` しか無かった。**
→ ★**旧SQWの事故が起きた場所と、守りが薄い場所が一致していた。**
★**守りの強さは「製品ぜんたい」では測れない**＝**表ごとに数える**。

### ⑵ 片付けと、そのあとの3段

- **重複1組（2行）を片付けた**＝どちらも回答に紐づかず、招待も未送信だった。
  ★**作成時刻が6分あいていた**＝**連打ではなく手で2回登録した**形
  （★画面の連打ガードがあっても「2回登録」は止まらない）。
- そのうえで**3段に重ねた**：

| 段 | 入れたもの | 止まるもの |
|---|---|---|
| 画面 | 送信中は押せない（`disabled`／`useRef`） | 連打 |
| サーバー | 追加の口を1つにして、同じメールがもう居たら足さない（★読めなければ足さない側に倒す） | 画面を通らない呼び出し・順番に2回 |
| **DB** | **（チーム×メール）の部分ユニーク** | ★★**同時に2回・どの経路からでも** |

★★**サーバーの段だけでは「同時に2回」が通る**ことを、**わざと確かめて検査に残した**
（`Promise.all` で同時に2回呼ぶと両方通る＝読んで→書く形の限界）。
★**検査が「これは期待どおり」と書いてある**ので、
**誰かが原子的な形にしたら検査が落ちて、書き直しを促す**。

### ⑶ 片付けのときに踏んだこと

★**対象人数を直す UPDATE を「チーム名」で絞ってしまい、同名のチーム3つに当たった。**
実害は無かった（3つとも「対象人数＝行数」が決まりの方式で、入った値は各自の行数だった）が、
★★**別の方式のチームが混ざっていたら、人が決めた目標値を上書きしていた**。
→ ★**本番の UPDATE / DELETE は必ず `id` で絞る**（[[mistakes]] 2026-10-16）。

## ★★実例：AI生成ジョブが3秒で5本走った（2026-10-15・SQW2）

**起きたこと**＝同じ人の同じレポートの生成ジョブが **3秒間に5本**作られ、
**5本とも AI を呼んで完成した**（中身の違うレポートが5つ保存された）。
★**止めたのは「1時間に5回まで」の上限**で、**6本目ならたまたま弾かれていた**だけ。

**原因**＝上限の判定が**読んでから書く**形だった。
同時に来た5本が全部「まだ0〜4本目」と見えて、**全部通り抜けた**（落とし穴⑴そのもの）。

### ここから分かる3つ

★**⑴「上限」は二重走行の守りにならない。** 上限は**回数を抑える**ものであって、
**同時に来たものを1本にする**ものではない。
★**しかも「上限でたまたま止まった」ことが、守れているように見えてしまう**
（5本で止まったのは設計の成果ではなく偶然）。
→ **同時に1本にしたいなら、束（誰の・何の・どの言語か）に対してユニークを張る。**

★**⑵「お金が動く」ものは、行の重複よりも損害が大きいことがある。**
名簿の重複は人数が狂うだけだが、**AI 呼び出しの重複はそのぶん原価が出る**
（この5本はそのまま費用になった）。
→ **「同時に2回」の検査は、お金・外部APIを呼ぶ口から先に入れる。**

★★**⑶ 索引の範囲は「作り直し（retry）」を外して考える。**
やり直しの仕組みがあるものは、**前の1本が走っている最中に次の1本を入れる**ことがある。
走行中（pending／running）をまるごとユニークにすると、**やり直しが必ず失敗する**
＝「お金を受け取ったのに何も届かない」に直結する。
→ **やり直しの行には印（`created_by='retry'` など）を付け、索引の条件から外す。**
★**外した側はアプリが見る**（走っている1本があれば、それを返して呼び直さない）。

### 直し方（2段・どちらか片方では足りない）

| 段 | 何をするか | 止まるもの／止まらないもの |
|---|---|---|
| アプリ | 走っている1本があれば、**その id を返して外部APIを呼ばない** | 順番に来た2回目は止まる／★**同時に来た分はすり抜ける** |
| DB | 束 × 言語 × … の**部分ユニーク索引**（走行中だけ・retry は除く） | ★**同時に来た分が止まる**（最後の砦） |

★**アプリ側は「索引がまだ無くても動く」形にする**＝索引を流す前から守りが1段効き、
流した瞬間に2段になる（**DB先・コード後が守れない場面の逃げ方**）。

### 検査でやったこと（★両方の世界を見せる）

- **索引あり**で同時に5回 → **1本・外部API 1回**／残り4つは同じ id を返す
- ★**索引なし**で同時に5回 → **5本・外部API 5回**（＝**索引が要ることの証明**）
- **同時に20回**でも増えるのは1本 → ★**上限の数え上げが水増しされない**ことを示す
- **retry は親が走っている最中でも入る**（やり直しを壊していない）
- 言語違い・テスト用・別の人・終わったあとは**止めない**

★**「索引なしの世界」を同じ検査の中で見せる**と、
**その索引を外した人が、何を失うのかをその場で知れる。**

## まとめ（次に作るときの順番）

1. ★**DB のユニーク制約を先に置く**（部分ユニークでよい・★既存の重複を先に片付ける）
2. **サーバー側で条件つき更新 or ユニーク違反を受ける**
3. **送る側で宛先を畳む**（症状をすぐ消せる）
4. **画面の `disabled`／`ref`**（★これは「親切」であって「守り」ではない）
5. **印は成功したときだけ・0通の理由を残す**
6. **検査は「同時に2回」を必ず入れる**

★★**1 を飛ばして 4 から作ると、画面を通らない道が残り続ける。**
