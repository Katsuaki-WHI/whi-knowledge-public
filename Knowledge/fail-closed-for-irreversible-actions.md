# 不可逆な操作のガードは fail-closed（確認できなければ止める）

**元に戻せない操作は、条件を確認できなかったときに「通す」のではなく「止める」。**
再試行すれば通るので運用は止まらない。逆に、確認できないまま実行すると元に戻せない。

## よくある落とし穴

ガードの判定を**真偽値**で書くと、読み取りに失敗したときの扱いが黙って決まってしまう。

```
const { data } = await db.select(...)   // ← error を受け取っていない
return (data?.length ?? 0) > 0          // ← 読めなければ false
```

これは「条件に当てはまらない」と同じ値を返す。つまり
**「確認したら該当しなかった」と「確認できなかった」が区別できない。**
削除のガードに使うと、**読めなかっただけで消せてしまう。**

★**気づきにくい理由**＝ふだんは読み取りが成功するので、テストも本番も通る。
壊れるのは、DBが一瞬不安定になった一度きりの瞬間。**そのとき消えたものは戻らない。**

## 直し方

**判定を「はい／いいえ／確認できなかった」の3つにする。**

```
type Check = "yes" | "no" | "unknown";
// 読み取りに失敗したら "unknown" を返す（ログには残す）
```

呼び出し側が用途に応じて倒す：

| 用途 | unknown をどちらに倒すか | なぜ |
|---|---|---|
| **削除・取り消せない実行** | **止める** | 確認できないまま実行すると戻せない。再試行で通る |
| **有料コンテンツの閲覧** | **見せない** | 確認できないまま見せると、権利のない人に渡る |

★**どちらも「危ないほうを選ぶ」だが、真偽値で見ると逆向きになる。**
「fail-closed に揃える」を**同じ boolean 値に揃えること**だと誤解しない。
**揃えるのは値ではなく、「確認できないときは危ないほうを選ぶ」という判断。**

## 合わせて守ること

- **エラーを握り潰さない。** `const { data } = await ...` と書くと error が消える。
  受け取って、少なくともログには残す（[[non-fatal-write-failure-and-column-mismatch]] と同根）。
- **止めたことを、利用者に伝える。**
  「できませんでした」で終えず、**もう一度試せば通る**ことが分かる言い方にする。
  例：「状態を確認できませんでした。もう一度お試しください」
- **同じ操作に複数のガードがあるなら、全部そろえる。**
  1つでも fail-open が残っていると、そこだけがすり抜け口になる。
- **画面で押せなくするだけで終わらせない。** 画面をすり抜けても、サーバー側で必ず止まること。
