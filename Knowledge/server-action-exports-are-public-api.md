# `"use server"` の export は公開 API。守りは「4種類だけ」に決めて、全件を機械で洗う

## 何が起きるか

`"use server"` を書いたファイルの **export した関数には URL が割り当たる**。
だから **画面から呼ばれていなくても、外から直接呼べる**。
画面側で隠しても、関数そのものに守りが無ければ中身は取れる・書ける。

**同じ型の問題は、1つ見つけたら必ず他にもある。**
ある製品では、最初の点検で「設定画面の46本」だけを直し、残り194本を
「鍵つきURL など別の守り方のもの」として**数えて出すだけ**にした。
翌日の点検で、その194本の中に**重大が39本**あった
（全メンバーの氏名＋メール・管理画面の鍵・個人向けURLの鍵・自由記述・
文面の書き換え・公開ストレージへの差し替え・全回答者の個票）。
その「194」という数字は毎回画面に出ていたが、**1日誰も開かなかった**。

## 守りは4種類だけに決める（これ以外を新しく発明しない）

| # | 守り | 使うところ |
|---|---|---|
| ① | 管理者のログイン判定 | 社内向けの操作 |
| ② | **鍵つきURL の照合**（鍵→対象を引く専用の関数） | URL が認証になっている画面 |
| ③ | **鍵を WHERE に使う**（`.eq("<鍵の列>", 受け取った鍵)`） | ②を部品にする前の素の形 |
| ④ | **同じファイルの守られた関数に、受け取った鍵をそのまま渡す**（取り次ぎ） | 束ねる関数 |

### ★素の ID を信じない
`teamId`・`settingId`・`roundId`・`projectId`・`jobId` のような**画面の裏の番号**を
引数で受けたら、**鍵から引いた ID と一致するかを必ず確かめる**。
一致の照合にだけ使い、**それ自体を鍵にしない**。
（上の重大の約半分が、この1行の抜けだった）

### ★公開 API にしたくない関数は、`"use server"` のファイルから出す
`import "server-only"` の内部モジュールに置けば **URL が割り当たらない**＝外から呼べない。
「画面からは呼ばないが、サーバーの別の場所（定期実行など）からは呼ぶ」関数は、
**守りを足すのではなく、置き場所を変える**のが正しい。

### ★検査は全件対象＋「公開でよい一覧」に理由を1件ずつ書く
「宣言した範囲だけきびしく見る」のは良い出発点だが、
**範囲の外を『参考』として出したまま放置すると、数字が出ているのに誰も見ない。**
→ 全 export を対象にし、**公開でよいものは理由つきの一覧（allow-list）に書く**。
一覧にも無く守りも見つからないものが**1件でもあれば落ちる**ようにする。
★一覧に「もう存在しない関数」が残っていたら、それも落とす（古い例外を放置しない）。

## DB の既定権限＝「GRANT を明示する」運用に変える

よくあるホスティング型の Postgres では、**新しく作った関数に匿名ロールの実行権限が
自動で付く**既定になっている。さらに PostgreSQL 自身の既定で **PUBLIC にも付く**。
＝**REVOKE を書き忘れた関数は、その瞬間から公開 RPC**。

実例：`SECURITY DEFINER` の保存用関数が公開されていて、
**公開鍵＋REST の RPC で、任意の対象に行を INSERT できた**
（鍵の照合が INSERT の後にあり、UPDATE にしか効いていなかった）。

- `alter default privileges … revoke execute on functions from <匿名>, <認証済み>, public`
- ★**匿名ロールだけ外しても足りない**（匿名ロールは PUBLIC の一員）。**PUBLIC からも外す。**
- ★表は RLS 有効＋ポリシーなしで止まるが、**`SECURITY DEFINER` の関数は RLS を越える**。
- `SECURITY DEFINER` には **`set search_path` を必ず付ける**。
- ★**trigger を返す関数は外さない**（REST は外に出さないので呼べず、
  外すと引き金が止まる危険だけが残る＝得るものが無い）。

## 順番：権限を閉じるときだけ「コード先・DB 後」

ふだんは **DB 先・コード後**（列が無い状態のコードを出さない）。
★**例外＝権限を閉じる（REVOKE・ポリシー削除）とき**。
いまのコードが匿名鍵で呼んでいるものを先に閉じると、その機能が止まる。
→ **先にコードを特権側に寄せ、本番に出してから閉じる。**

## 守りを足す作業は「行き過ぎ」も欠陥になる

URL を渡して見せ合うことが仕様の製品では、**URL で開ける範囲を狭めたら
それは直しではなく欠陥**になる。
→ 直す前に「**誰が・どの URL で・何を見られるか**」の一覧を作り、**検査に落とす**。
検査を2つに分ける：

- **A＝守る**（見える範囲を狭めていない）… **直しの前も後も通らなければならない**
- **B＝塞ぐ**（番号だけでは取れない）… **直したあとだけ通る**

★A が「直す前のコード」でも通ることを確かめると、**行き過ぎていない証明**になる。
★B が「直す前のコード」では落ちることを確かめると、**塞いだ穴が実在した証明**になる。
（実例＝A は前後とも 30/30、B は前 1/71 → 後 71/71）

★検査そのものが本物かを確かめるには、**わざと1本だけ守りを外して、落ちることを見る。**
