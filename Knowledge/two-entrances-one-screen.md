# お試し用の運営画面は「同じ画面・入口を2つ」にする（画面を2つ作らない）

相手に運営を任せたいが、**戻せない操作だけは自分に残したい**ことがある。
このとき**画面を2つ作ると、必ず片方が古くなる**（同じ機能を2回直すことになり、
片方だけ直した日から挙動が食い違う）。

★**画面は1つ。入口（URL）を2つにして、入口で権限を変える。**

## 決めておくこと

1. **どちらの入口から来たかを、サーバー側で判定する。**
   画面の出し分けだけにしない（URL を知っていれば叩けるため）。
2. **できないことを「隠す」より「押せない理由をその場に出す」**。
   消すと、相手は機能を探し続ける（[[2026-08-26-ui-design-principles-visibility-confirmation]]）。
3. ★**誰が操作したかを記録する。** 入口が2つある＝操作者が2種類いる、ということ。
   記録が無いと、あとで「どちらがやったか」を誰にも説明できない。
4. **渡した URL は、渡した側が無効化・再発行できる**ようにする。
   ★鍵は**ハッシュで保存**し、原本は発行のときだけ表示する（控えを持たない）。
5. **期限は「付けられる・既定は付けない」**。
   既定で切れる作りは、当日戻れない人を生む（実害が大きいほうを避ける）。
6. ★**相手の入口からは、相手にさせたくない画面への入口を1つも出さない。**
   リンクを残すと「押したのに何も起きない／権限がないと言われる」になり、
   押した人が自分を責める（[[one-slot-two-states-not-two-buttons]]）。

## よくある落とし穴

- **ガードを「入口」ではなく「データの形」で書いてしまう。**
  例＝「外部の ID が入っている行は管理対象外」とすると、
  **別の目的で同じ ID を入れた行まで巻き添えになる**。
  ★**「どこから来たか（由来）」を表す列を持ち、由来で判定する。**
  データの形は、由来の代わりにはならない。
- ガードが**何か所にあるかを数えずに**仕様を変える。
  変えるなら **grep で全件を一覧にして、1つずつ扱いを書く**。
