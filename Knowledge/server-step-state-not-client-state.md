# 複数回のやり取りにまたがる段取りは、画面の状態でなくサーバーの状態に持つ

**【Public可】**

## 何が起きたか

2段階確認（認証アプリ）の登録画面を、
**①はじめる → ②QRを出す → ③6桁を照合 → ④予備コードを見せる** の4段で作った。
段取りを画面側の状態（React の `useActionState`）に持たせたところ、
**③で6桁を間違えた瞬間に、②で出した QR も含めて全部消え、①に戻った。**

- エラーは出ない。ビルドも型チェックも通る。
- **画面の状態は、送信のたびの作り直しで消えることがある**（作り直しが起きるかどうかは、
  そのやり取りが何をしたか＝Cookie を書いたか、再描画が走ったか、に左右される）。
- 困るのは「消えること」より **「消えたことに気づけないこと」**。
  間違えた人からは「やり直したら最初に戻った」としか見えない。

## どう直したか

**段取りそのものをサーバー側（HttpOnly の署名つき Cookie）に持ち、
やり取りのたびに `redirect` で同じ URL に戻す。**
画面は「いまのサーバーの状態」を読んで、どの段かを決めるだけにする。

```
①～④ の段 … Cookie の中身で決まる（読み込み直しても同じ段に戻る）
やり直してほしいこと … URL の ?e=<辞書の鍵> で渡す（文言はコードに書かない）
```

結果＝**間違えてもQRは消えない／読み込み直しても同じ段に戻る**。
確認もそのまま書ける（「断られてもQRが残っているか」「読み込み直しても戻るか」）。

## 判断の線

- **1回のやり取りで終わるもの**（押す→結果が出る）＝画面の状態でよい。
- **人の操作を挟んで複数回にまたがるもの**（QRを読み取る・コードを控える）＝**サーバーに持つ**。
- ★**「もう一度やり直してほしい」ときに消えて困るものがあるか**で決める。

## あわせて踏んだ落とし穴

★**`signOut()` は「手元の記録を消す」ではなく「そのセッションを失効させる」。**
片付けのつもりで各処理の最後に呼んだところ、**次のやり取りでそのセッションが使えなくなった**
（`Auth session missing!`）。失効させるのは**本当に最後の1回だけ**にする。

★**認証アプリの既定は「無効」**（Supabase CLI の `[auth.mfa.totp] enroll_enabled = false`）。
ローカルで試すときも、本番に入れるときも、**先に有効になっているかを確かめる**。

## 検証の型

- 段取りのある画面は「**間違えたとき**」と「**読み込み直したとき**」を必ず通す
  （正しい道だけ通しても、この種の消え方は見つからない）。
- 6桁コードのような**30秒で変わるもの**は、窓の残りが少ないときに取ると落ちる。
  **残りが5秒以上ある時だけ取る**（★回数の上限つきで待つ）。
  そうしないと、同じコードで通ったり落ちたりして「直ったのか」が分からない。
