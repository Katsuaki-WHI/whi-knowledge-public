# 同じIDのまま文言を変えるときは、旧い文言を2か所に残す

設問・選択肢・区分ラベルなど、**IDで集計しているものの文言を変えるとき**の話。

## 何が起きるか
`question_id` を変えずに文言だけ変えると、**集計はそのまま連続する**（グラフも平均も切れない）。
これは利点だが、同時に**「いつの文言に対する回答か」が分からなくなる**。

★とくに **設問文をDBに保存していない設計**（保存するのは ID と点数だけ）では、
**DBを見ても文言の履歴は一切残らない**。コードの現在版が上書きされれば、旧い文言はどこにも無くなる。

## やること
**旧い文言を、必ず2か所に残す。**

1. **コードのコメント**（その設問の直前）＝次にコードを読む人が、変更があったことに気づける
2. **決定の記録**（Decisions）＝なぜ変えたか・いつ変えたかと一緒に

書く内容は3つ：**旧文言（日英とも）／変更日／変更理由**。
「◯月◯日より前の回答は旧文言に対する回答」と**はっきり書く**。読む人が経年比較で判断できる。

## 過去データは書き換えない
旧文言に対する回答を、新文言の回答として扱い直したりしない。**回答時点の事実を変えない。**
集計が連続することと、文言が同じであることは別の話。混ぜない。

## 変更の影響を、IDの周りまで確認する
文言を変えると**主語や対象が変わる**ことがある（例：「組織には〜」→「組織の経営層は〜」）。
そのとき、**そのIDに紐づく設定が影響を受けないか**を確認する：
カテゴリ、グループ分けの一覧、表示ラベル、前置き文との整合。
※今回は設定側の変更は不要だったが、**確認したこと自体を記録に残す**と次が速い。

## 厳密にやるなら
経年比較を厳密にやるなら、**回答レコードに「設問の版」を記録する**のが本筋。
実装していないなら、**記録で担保していることを明示する**（「今は記録で担保・将来は版の記録が必要」）。
曖昧にしておくと、数年後に「この数字は比較していいのか」が誰にも分からなくなる。

## 確認のしかた
文言の変更は、**画面に渡る値そのもの**を見て確かめられる
（設問を組み立てる関数を呼んで、新旧・日英・他の項目が変わっていないことを機械で照合する）。
描画側がその値を**加工せずそのまま出す**なら、値の確認が表示の確認になる（加工しているなら画面で見る）。
