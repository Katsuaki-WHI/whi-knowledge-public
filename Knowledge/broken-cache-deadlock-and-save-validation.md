# 壊れたキャッシュの袋小路と、保存前検証の欠落

生成結果をキャッシュに持つ機能で、**壊れた生成物が「成功」として保存され、しかもそれを作り直す手段が塞がれる**という、
2つの欠落が重なると **1件だけ・特定の人だけが永久に直せない**状態になる。実際のお客さまの有料レポートで発生した。

## 起きたこと（あるプロダクトの有料レポート・2026-09-11）

実決済（550円・live）で購入した人のレポートが「データ形式エラー」で開けず、
画面の生成ボタンを押すと「jobId not returned」で**再生成もできなかった**。

原因は3層に分かれていた。

### ① 生成物が壊れていた（AI側・非決定的）
AI の Tool Use（構造化出力）が、**7章のうち1章だけを JSON オブジェクトではなく JSON 文字列で返し**（二重エンコード）、
**しかもその文字列の末尾に閉じ括弧 `}` が1つ余分**についていた。

```
..."closing": "——さあ、行くがよい。"\n}\n}
                                      ↑ この1つが余分
```

既存の救済パース（`JSON.parse(章の文字列)`）は、この余分な1文字で SyntaxError になり救済できなかった。
★**二重エンコードの救済を入れていても「余分な閉じ括弧つきの二重エンコード」までは届かない。**

### ② 保存前に検証していなかった（残り方の問題）
生成側（Edge Function）は正規化は通すが **「全章がオブジェクトか」を検証していなかった**ため、
壊れた出力をそのまま保存し、ジョブを `completed` にしていた。
★**エラーログも失敗ジョブも残らない**＝「生成は成功している」ようにしか見えず、調査の手がかりが画面のエラー文言しかない。

### ③ 作り直す手段が塞がれていた（袋小路・これが本当の事故）
生成APIが **「キャッシュ行があるか」だけでキャッシュを返して打ち切っていた**。
中身が正しいかは見ていない。新規ジョブを作って `jobId` を返す分岐はその後ろにあるため、
**壊れたキャッシュ行がある限り `jobId` は絶対に返らない**。
強制再生成のフラグは管理者限定だったため、**本人にも運営者にも逃げ道が無かった**。

## 一般化して守ること

1. **保存の前に検証する。** 生成系は「返ってきた＝成功」ではない。
   期待する形（必要なキーが全部あるか・型が合っているか）を**保存の直前に確かめ、通らなければ保存せず失敗として記録する**。
   壊れたものを「成功」として残すと、**壊れている状態と正常な状態が見分けられなくなる**。
2. **キャッシュを返す条件は「ある」ではなく「使える」。**
   キャッシュの有無だけで早期リターンすると、壊れた1件が永久に固定される。
   **中身が使えないなら、キャッシュが無いときと同じ道（作り直し）へ進ませる。**
3. **逃げ道を管理者専用にしない。**
   「作り直す」が管理者限定だと、壊れた人は自分では何もできない。
   管理者に連絡が来なければ、**壊れたまま気づかれない**。
4. **救済（防御的パース）は「ありうる壊れ方」を1つ足すたびに弱くなる。**
   救済は入口を広げる対症療法。**本命は②の保存前検証**（そもそも壊れたものを残さない）。
5. **エラー文言は実態と合わせる。**
   今回の画面は「古い形式です（v3.0でJSON形式に変更されました）」と出ていたが、実体は「1文字多い」。
   ★**バージョン列がハードコードされていて、画面はそれを見てすらいなかった。**
   文言が原因を誤って指すと、調査が最初から間違った方向へ行く。

## 調査の型（同じことが起きたとき）

- **「古い形式です」を信じない。実データを取り出して、何がどう違うのかを目で見る。**
- 表示側と**同じ判定ロジック**をコピーして全件に回すと、影響範囲が分単位で確定する
  （今回：完了購入63件を全件検証して**壊れているのは1件だけ**と確定できた）。
- 直前のデプロイを疑うときは `git diff --name-only <前>..<後>` で**その経路のファイルが含まれるか**を見る
  （今回は0件かつ、壊れたデータの作成日がデプロイより前＝無関係と確定）。

## 修復するときの型（本番データを1行だけ直す）

1. 書き換え前の行を**丸ごとバックアップ**し、**sha256 を記録**する。
2. 更新の直前に**もう一度 sha256 を照合**し、一致しなければ中断する（間に誰かが変えていたら上書きしない）。
3. 修復後の値を、**表示側と同じロジック**で検証してから UPDATE する。
4. **余計な列を触らない**（生成時刻 `updated_at` を書き換えると「いつ作られたか」の記録が歪む）。
5. **実画面を開いてスクリーンショットを自分で見る**。機械的な検証だけで終わらせない。

## 対処済み（2026-09-11・本番反映）

上の3つの欠落を、実際に塞いだ。**壊れていた1件はデータ修復で復旧し、同じことが起きても自力で直る形にした。**

| | やったこと |
|---|---|
| (a) 袋小路 | キャッシュを返す条件を**「あるか」→「使えるか」**に変更。使えないキャッシュは無かったものとして生成へ進む＝`jobId` が返り、本人の生成ボタンで作り直せる |
| (b) 救済 | 章の文字列がパースできないとき、**末尾の余分な閉じ括弧を1つだけ**落として再挑戦。★**1つだけ**に限る（何度も削ると、途中で切れたデータまで「読めたことにして」欠けたまま保存する） |
| (c) 保存前検証 | 生成側で章がそろっているか検証し、**通らなければ保存せず失敗として記録**（どの章がどう壊れたかを残す）。従来は壊れた出力を保存して「成功」にしていた |
| (d) 死にコード | 画面から到達できない再生成の一式を削除（残すと「ここから直せる」と誤読される） |

### 実装で効いた判断

- **判定は1つの関数に集約する。** 「このキャッシュは使えるか」を画面ごとに書くと、直した場所と実際に効く場所がずれる。API・表示ページ・生成処理が同じ窓口を通るようにした。
- **同じ構造の兄弟にも同時に当てる。** 片方（兄弟にあたる別種のレポート）には救済も検証も無かった。
  **「同じ形をしているのに片方だけ直す」は、次に壊れる場所を残すだけ。**
- **逃げ道は管理者専用にしない。** 正常なものの作り直しは管理者のみのままでよいが、
  **壊れているものは本人が直せる**必要がある（管理者に連絡が来なければ、壊れたまま気づかれない）。

### 検証で効いた型

- **救済関数は「救うもの」と「救わないもの」を同数くらい書く。**
  余分な括弧1つは救い、2つ余分・途中で切れた・旧形式は**救わない**ことをテストで固定した。
  救済は広げすぎると「壊れたものを通す」側に倒れるため、**通さない側のテストのほうが大事**。
- **既存データ全件を、新しい判定関数そのもので通す。** 「直したつもりが既存を壊していない」を数で示せる。
- **最後は実物で1回通す。** 壊れたキャッシュを作り、**本人の生成ボタンを1回押して復旧する**ところまで。
  部品のテストが全部通っても、経路がつながっている保証にはならない。
