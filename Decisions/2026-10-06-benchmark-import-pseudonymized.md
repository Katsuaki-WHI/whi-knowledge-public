# 過去データを物差しにするときの個人情報の扱い（仮名加工情報として扱う）

★**Public 可**（固有名詞・顧客名・本番の列構成を含まない。社内の具体は Private 側）。

## 0. 1行

**ID を別の値に変換しても、元のシステムに「ID → 連絡先」の対応表が残っているなら、
個人情報の区分は変わらない。だから変換に手間をかけず、消すものを消し、
残した ID は管理の仕組みで守る。**

## 1. なぜ「変換」で安心してはいけないか

過去データを物差し（平均・ふつうの幅・相関）にするとき、
「ID をハッシュに変換したから匿名になった」と考えてしまいやすい。

★しかし**自分たちが対応表を持っているかぎり、自分たちは戻せる**。
この「容易照合性」がある状態では、変換してもその情報は**仮名加工情報**であって、
個人情報の枠から出ない。**変換は、守りを増やさないのに作業と事故（取り違え）を増やす。**

## 2. やること

**⑴ 消すものと残すものを、列の名前で決める**（「それらしいもの」を機械で探さない）

| | 例 |
|---|---|
| **消す** | 名前・連絡先・自由記述・組織名 |
| **残す** | 元の回答ID・組織ID・業種・規模・部署・役職・**日付** |

- ★**組織名は物差しに不要**（組織ID で足りる）。
- ★**日付は残す**＝**時期の影響は分析に必要**（景気・季節・期首期末）。
  「細かいと特定に寄るから月に丸める」は、**分析の側を壊すほうが損が大きい**。
- ★**区分（業種・規模）が無い行は「不明」として全体平均にだけ使う**
  ＝行ごと捨てない（母数は保つ）。切り口別には出さない。
- ★**自由記述は消す**＝個人がいちばん出る場所で、物差しには使わない。

**⑵ 残した ID は「管理の仕組み」で守る**

1. **対応表と物差しのDBを分けて管理し、触れる人を限る**
2. **外部（販売パートナー・会員）には集計値だけ。生データは出さない**
3. **社内規程に「仮名加工情報」と書く**（★法律の最終判断は専門家に確認する）

## 3. 物差しそのものの決め方（あわせて決まったこと）

- **古い版の基準値を土台にし、新しい版の回答は対応表で同じ土台に乗せる。**
- ★**土台に対応が無い設問は混ぜない＝新しい版だけの別枠に蓄える。**
  無いものを「近い設問」で埋めると、**物差しのほうが歪む**。
- **閾値（段階の境目）は据え置き。ただし置き場所をコードの定数から
  一元管理テーブルへ移す**＝見直した瞬間に全レポートへ反映される形にする。
  移すときは「表を作る → 今の定数と同じ値を1行目に入れる（表示は変わらない）→
  読めなければ定数に戻る形で参照を付け替える」の順にする。

## 4. 順番

★**実装の前に「いまのDBに何が残っているか」を読むだけで全部数える。**
消すものを消し損ねる／残すものを捨てる事故は、ここを飛ばしたときに起きる。
