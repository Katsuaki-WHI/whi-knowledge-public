# セキュリティの土台（構造だけ・2026-10-05）

ある製品のセキュリティ点検（重大9／中21／軽12）の直しで決めた
**「これ以後、全部これに従う」決まり**の、**構造の部分だけ**。
個別の直しや製品の中身は含めない。

---

## 0. いちばん上の原則＝**URL を持っていること自体が認証**

「URL を渡して使ってもらう」ツールでは、守りの中心はパスワードではなく **URL そのもの**。

- 鍵は推測できない長さで作る。
- ★**URL で開ける範囲は、セキュリティの直しで狭めない。** 狭めたら、それは直しではなく欠陥。
- **塞ぐ対象は「URL を持たない人が、画面の裏の番号（内部ID・メールアドレス）だけで
  中身や鍵を取り出せる経路」だけ。**

### ★この原則を機械で守る＝A／B の2本立ての検査

| | 見るもの | いつ通らなければならないか |
|---|---|---|
| **A（守る）** | 「見られる・できる」が1つも減っていない | ★**直す前も、直したあとも** |
| **B（塞ぐ）** | 素のIDだけで中身や鍵が取れない | 直したあとだけ |

★**A を「直す前のコード」に当てて満点になることを必ず確かめる。**
これが**行き過ぎの歯止め**になる（守りを足す作業は、放っておくと商品を壊す）。
★**B が「直す前」でほとんど落ちること**が、塞いだ穴が実在した証明になる。

---

## 1. 守りは4種類だけ（これ以外を新しく発明しない）

サーバー側の関数を「画面から呼べる形」で export すると、
**画面から呼ばれていなくても URL を持つ公開 API**になる。
画面で隠しても、関数そのものに守りが無ければ中身は取れる・書ける。

| # | 守り |
|---|---|
| ① | 管理者のログインを確かめる |
| ② | 鍵つきURL の照合（道具を1ファイルに集める） |
| ③ | **鍵を WHERE に使う**（受け取った鍵で行を絞る） |
| ④ | **同じファイルの守られた関数に、受け取った鍵をそのまま渡す**（取り次ぎ） |

★**公開でよいものは、理由を1件ずつ言葉にして一覧に書く。**
一覧に無い・守りも見つからない export が**1件でもあれば検査が落ちる**ようにする（★数で逃げない）。

### ★素の ID を信じない
内部ID やメールアドレスを引数で受けたら、**鍵から引いた ID と一致するかを必ず確かめる**。
一致の照合にだけ使い、**それ自体を鍵にしない**。（重大の半分が、この1行の抜けだった）

### ★公開 API にしたくない関数は、export の対象から出す
「サーバー専用」と宣言した内部モジュールに置けば **URL が割り当たらない**＝外から呼べない。
メール送信・個人情報の読み書き・監査ログの書き込みは、ここへ移すのが基本。

## 2. データベースの既定権限＝**GRANT を明示する運用**に変える

詳しくは [[mistakes]] 2026-10-05 の2件。要点だけ。

- 新しい表・関数に**公開ロールの権限が自動で付く**（さらに PostgreSQL の既定で PUBLIC にも付く）。
  ＝REVOKE を書き忘れた表は、その瞬間から公開。
- ★**RLS は TRUNCATE を止めない**（RLS で守っているつもりの表も、まるごと消せる）。
- ★**既定権限では「関数の PUBLIC EXECUTE」は閉じられない**（関数は migration ごとに REVOKE を書く）。

---

## 3. AI に渡す前に、連絡先を隠す

- 隠す＝**メール・電話・URL**。
- ★**氏名は隠さない**（名前で語ることが成果物の核なら、隠すと商品が成立しない）。
- ★**検査には「隠すもの」と同じ数だけ「隠してはいけないもの」**を並べる。
- ★**実物のプロンプトを通して「1文字も変わらない」ことを確かめる。**
- ★**本人の言葉を正確に引用する設計の文章には掛けない**（引用の照合が崩れる）。

---

## 4. 鍵と Cookie

- **用途ごとに鍵を分ける**（1つの鍵の漏れが、別のものにまで効かないように）。
- ★**未設定でも今までどおり動くようにし、ログに警告を出す**（設定の前に止めない）。
- ★★**鍵を取り替えるときは、古い鍵でも読めるようにしておく。**
  そうしないと設定した瞬間に**覚えている人全員のものが消える**。
- **Cookie の名前と期間は変えない**（覚えている人がそのまま使える）。
- **パスワードの比較で長さを漏らさない**（いったん同じ長さに直してから比べる）。

---

## 5. 回数制限（レートリミット）

★**回答・結果の閲覧・招待には掛けない。**
同じ回線から大勢が一斉に使う場面があるため、回線単位の制限は**正しい利用者を止める**。

掛けるのは3つだけ＝**管理のログイン**／**AI 生成の起動**／**合言葉の照合**。

★**数える場所に新しい表を作らなくてよい**＝既にある監査ログの行を数えれば、
**サーバーのインスタンスをまたいで数えられる**（成功したら自然に数えが戻る形にする）。

★★**回数の上限を「読むとき」に掛けてはいけない。**
買った人が自分の成果物を開けないのは守りではなく欠陥。
**権限の確認は読む手前／回数の上限は重い処理を呼ぶ手前**に分ける。

---

## 6. 外に返すエラー文は定型に

生のエラー文は、**認証を通っていない口からは返さない**（中の作り・表の名前が出る）。
★詳しい理由は**サーバーのログに残す**。
★**管理のログインを通った先では生のメッセージを返してよい**（直すのに要る）。

---

## 7. 順番の決まり

- **DB 先・コード後**が原則。
- ★**例外＝権限を閉じるときは「コード先・DB 後」。**
  いまのコードが公開ロールで呼んでいるものを先に閉じると、その機能が止まる。
- **戻す SQL に番号を付けない**（番号を並べると順番を間違えて先に実行される）。
- **足した列は戻すときに落とさない**（値が消えて戻らない）。

---

## 8. 残す穴は「承知のうえ」と書いて残す

閉じられない穴（コードの作り替えが要るもの）は、
**何が・なぜ残っているか・いつ閉じるか**を表にして記録に残す。
「あとで」と書いて宙に浮かせない。
